화면은 움직였는데 캡처는 그대로였다

사용자 신고: “스크린샷을 찍어도 엉뚱한 곳을 보여주거나, 계속해서 동일한 부분만 찍힌다.” 앨범에 쌓인 8장 중 6장이 바이트까지 동일했고, 8장 전부가 사용자가 보고 있던 장면이 아니라 링크의 원본 사진구체였다. 원인은 렌더가 아니라 포즈였다 — 캡처가 화면이 아니라 갱신이 멈춘 거울을 찍고 있었다.

증상: 캡처 고정 · 오촬영 결함 2건 webui/app.js 회귀 항목 ⑥ 캡처 추가

1. 한 줄 요약

사진구체 링크에서는 파노라마 → 탭 포즈 동기화가 한 번도 켜지지 않았다. 날것의 CIHM… id 를 기다리도록 무장해 놓고 화면에는 감싼 CAoS… id 를 띄웠기 때문이다. 둘은 영원히 같아지지 않으므로 syncArmed 는 계속 false 였고, 그 탭의 포즈는 링크에서 읽은 값에 얼어붙었다. 사용자가 아무리 이동해도 캡처는 같은 이미지 URL 을 다시 받았다.
링크 CIHM0ogK…→ SDK 는 CAoS… 로 띄움→ 무장 조건 = CIHM… 불일치→ 포즈 동결→ 캡처 = 링크 원본

두 번째 결함이 이것을 완성했다: 제3자 파노를 자체 구체 뷰어로 띄울 때, 그 뷰어가 자기 출처(파노 id · 이미지 토큰)를 탭 포즈에 적지 않았다. 그래서 설령 동기화가 살아 있었더라도 캡처는 직전 장면의 이미지 URL 을 계속 썼을 것이다.

그리고 그 3개조차 화면이 아니었다

스크린샷의 뷰어에는 브라치섬 북안(수페타르·스플리트스카 방면) 해안도로가 떠 있고 저작권은 © Smokvina Travel Denis Orlić 였다. 그런데 저장된 캡처는 전부 섬 남안의 즈라트니 라트 드론 사진구체이고, 하단 지도 핀도 거기에 찍혀 있다. 같은 섬이지만 15km 남짓 떨어진 다른 해안이다.

가장 나쁜 실패 지오게서 복기 도구에서 “조용히 다른 장소를 분석한다”는 것은 틀린 답을 근거까지 붙여 내놓는 일이다. 검은 화면은 사용자가 알아채기라도 한다.

3. 원인 ① — 무장이 켜지지 않았다

헤드리스 브라우저로 실제 앱을 돌려 상태를 그대로 읽었다. 추측이 아니라 계측이다.

파노라마는 링크 탭이 몇 개든 하나다. 그래서 “지금 이 파노라마가 보여주는 것이 어느 탭의 것인가”를 못 박기 위해 armWhenLoaded() 가 있다 — 요청한 파노가 실제로 올라온 뒤에만 파노라마 → 탭 기록을 허용한다. 그 판정이 문자열 하나였다.

// v0.4.1 — initSplit()
armWhenLoaded(myToken, pose.pano, tabId);        // 날것 CIHM… 로 무장
svc.getPanorama({ pano: pose.pano })
  .catch(() => svc.getPanorama({ pano: pose.pano_alt })
    .then(() => {
      syncWantPano = pose.pano_alt;              // ← 전역만 바꿨다. 클로저는 그대로.
      pano.setPano(pose.pano_alt);               // 화면에는 CAoS… 가 뜬다
    }));

// armWhenLoaded 안쪽
if (wantPano && pano.getPano() !== wantPano) return false;   // 영원히 false

v0.3.4 에서 “사진구체 id 는 감싸면 SDK 가 안다”는 것을 발견해 pano_alt 경로를 추가했는데, 그때 무장 조건을 같이 옮기지 않았다. syncWantPano 전역에는 대입했지만 판정하는 것은 armWhenLoaded 가 잡아 둔 지역 변수였다. 한 줄이 두 곳에 있었고 한 곳만 고쳤다.

계측 (수정 전)

after move : armed=false  shown=CAoSF0NJSE0w…  cur.pano=CIHM0ogK…  cur.lat=45.0999   ← 그대로
capture    : mode=photo_url  pano_id=CIHM0ogK…  lat=45.0999              ← 화면과 다른 파노
             (화면의 실제 위치는 45.10012)

동기화가 꺼져 있으면 syncFromPano() 가 첫 줄에서 반환한다. 그래서 함께 죽은 것들:

  • 탭 포즈(t.current) — 캡처·보고서가 쓰는 그 값
  • 지도 중심과 마커 — 로드뷰를 이동해도 지도가 따라가지 않았다
  • 포즈 카드 — 화면과 다른 좌표를 계속 표시했다
  • reportViewerState() — “표시 중” 줄이 갱신되지 않았다

공식 파노 링크에서는 이 경로를 타지 않아 정상이었다(armed=true). 그래서 증상이 사진구체 링크에서만 나왔고, 재현 조건을 좁히는 데 시간이 걸렸다.

4. 원인 ② — 뷰어가 자기 출처를 적지 않았다

v0.4.0 의 규칙: 제3자 파노는 항상 자체 구체 뷰어로 띄운다. 그런데 무엇을 띄웠는지는 아무도 기록하지 않았다.

// v0.4.1 — useOwnViewer(id)
gpmsToken = r.base;          // 서버가 알아낸 이 파노의 이미지 토큰
gpmsBlocked = true;
startSphere({ …, pano: id }, t.id);
// t.current.photo_url 은 여전히 링크의 !6s — 즉 이전 장소의 이미지다

캡처는 서버에서 pose.photo_url 로 이미지를 다시 받는다 (capture.photo_url_for() 가 현재 시점으로 URL 을 재조준한다). 그러니 화면을 바꿨으면 그 값도 바꿔야 한다. 안 바꾸면 “지금 화면 캡처”가 정확히 이전 장면을 찍는다 — 그것도 현재 시점 각도로 겨눠서, 그럴듯하게.

두 결함은 서로를 가렸다. ①만 고치면 사진구체 파노에서 photo_url 이 사라져 정적 API 로 떨어지고, 정적 API 는 이 파노를 모른다 — 캡처가 통째로 실패했을 것이다. ②만 고치면 동기화가 죽어 있으니 아무 효과가 없다. 둘을 같이 고쳐야 사용자의 증상이 사라진다.

5. 스위트는 왜 또 못 잡았나

tests/viewer_matrix.py 는 바로 이런 회귀를 잡으려고 만든 것이다. 6개 링크 전부 ✔ 였다.

스위트가 재던 것이번 고장
① 렌더 — 제3자 파노가 그려지는가(밝기)정상이었다. 화면은 멀쩡했다.
② 출처 — 픽셀이 /api/pano-image 를 거쳤는가정상이었다.
③ 조작 — 진짜 드래그로 화면이 바뀌는가정상이었다.
④ 이동 — 로드뷰맨을 옮기면 화면이 따라오는가정상이었다. 화면은 따라왔다.
⑤ 탈출 — 새로고침 버튼이 눌리는 자리인가정상이었다.
⑥ —캡처 버튼을 한 번도 누르지 않았다.

6. 고친 방식

거울을 고치되, 거울에 의존하지 않게 만든다.

①무장은 SDK 가 돌려준 id 로

getPanorama() 응답의 location.pano 로 띄우고 그 id 로 무장한다. 판정은 두 증거 중 하나면 통과 — ⓐ 요청한 id 들(날것·감싼·정식) 중 하나가 떴다, ⓑ 아니어도 화면의 파노가 이 로드 직전과 달라졌다.

ⓑ 가 있어야 “영원히 무장 안 됨”이라는 조용한 고장이 원천적으로 안 생긴다. 원래 지키려던 성질(이전 탭 좌표가 새 탭에 새지 않음)도 그대로다 — 로드 전에는 화면이 여전히 직전 파노이므로 어느 조건도 성립하지 않는다.

②캡처는 거울이 아니라 화면을 읽는다

새 함수 livePose() 가 캡처 직전에 표시 상태에서 포즈를 만든다. 구체 뷰어면 그 구체의 원본 토큰과 sphere.getPov(), 정지 이미지 폴백이면 그 이미지의 조준값, 구글 뷰어면 그 파노의 id·좌표·시점.

동기화가 어떤 이유로든 죽어도 캡처는 틀리지 않는다. 같은 실패가 다시 나도 사용자에게는 닿지 않는다 — 이것이 이번 수리의 핵심이다.

③뷰어가 자기 출처를 기록한다

noteSphereSource() 가 구체를 띄우는 순간 파노 id·이미지 토큰·좌표를 탭 포즈에 적는다. 포즈 카드도 그 즉시 그 값을 보여준다 — 카드가 말하는 것과 캡처가 찍는 것이 같아진다.

④같은 파노의 두 이름을 같게 본다

samePano() 가 날것 CIHM… 과 감싼 CAoS… 를 동일시한다(둘 다 이 탭 링크의 id 일 때만). 덕분에 제자리에 있는 동안에는 링크가 준 !6s 이미지를 버리지 않는다.

⑤고장이 재발하면 화면이 말한다

직전 캡처와 파노·좌표·시점·원본이 모두 같으면 그 사실을 알린다. 같은 자리에서 두 번 찍은 것이면 무시하면 되고, 화면을 옮겼는데 이 문구가 나오면 그것이 곧 이 고장의 재발 신호다.

7장이 쌓인 뒤 사용자가 발견하는 대신, 2장째에 도구가 말한다.

⑥스위트가 캡처를 찍는다

viewer_matrix.py 에 ⑥ 항목 추가 — 이동 전후로 실제 캡처 버튼을 누르고 ⓐ 두 장의 바이트가 달라졌는가 ⓑ 캡처 좌표가 화면이 보여주는 좌표와 80m 이내인가를 잰다.

기준 좌표는 currentPose(거울)가 아니라 표시 상태에서 읽는다. 거울로 거울을 검사하면 아무것도 검사하지 못한다.

부수적으로 같이 바로잡은 것

구체가 떠 있는 동안 밑에 깔린 파노의 시점이 사용자가 돌려 둔 방향을 덮지 않는다 — 시점의 주인은 화면에 보이는 쪽이다.
syncFromPano() 의 fov 가 다른 탭의 값(currentPose.fov)을 참조하던 것을 그 탭 자신의 값으로 고쳤다.
탭을 전환하면 포즈 카드가 링크 원본(t.extracted)을 그리던 것을 현재 포즈(t.current)로 바꿨다 — 카드는 캡처가 찍을 것을 말해야 한다.
다른 파노로 옮겨가면 pano_kind 배지를 뗀다. 그 라벨은 링크의 파노를 분류한 값이라 이동 후에는 사실이 아니다.
캡처 버튼 잠금이 포즈 갱신(renderPose → updateActionButtons) 때문에 곧바로 풀리지 않도록 순서를 바로잡았다.

  • 실제 GPU(헤디드) 실행은 아직 안 했다. 헤드리스 6/6 통과가 전부다.
  • CIAB 링크의 이동·캡처는 미판정이다 — 재현장치가 다른 파노를 못 잡았다. “통과”가 아니라 “못 쟀다”이다.
  • WebGL 이 없어 <img> 폴백으로 떨어지는 경로는 livePose() 가 같은 규칙으로 다루지만, 그 경로의 fov 는 수평/수직 변환이 한 단계 생략돼 캡처 화각이 화면과 미세하게 다를 수 있다. 실측하지 않았다.
  • 동일 장면 알림은 연속 두 장만 본다. 사용자가 A→B→A 로 돌아와 찍으면 알리지 않는다.
