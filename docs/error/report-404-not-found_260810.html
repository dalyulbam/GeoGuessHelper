보고서 생성 시 “보고서 실패: Not Found”

캡처 6장을 모은 뒤 보고서 버튼을 누르면 이 메시지만 뜨고 아무 일도 일어나지 않는다. 원인은 내가 만든 회귀다 — 작업 큐를 도입하면서 구 API 경로를 제거했는데, 브라우저가 캐시된 예전 app.js 로 그 사라진 경로에 POST 하고 있었다. 캡처 장수와는 아무 관련이 없다.

증상: 보고서 실패: Not Found (HTTP 404) 원인: 구 라우트 제거 + 브라우저 캐시 수정: 호환 라우트 복원 + ?v= 캐시 무효화 해결됨 — HTTP 200
Symptom

증상

보고서 버튼을 누르면 즉시(작업이 시작되지도 않고) 실패 토스트가 뜬다.

캡처 6장→ 보고서 생성 클릭→ 보고서 실패: Not Found
단서 1 — 메시지 문구. 새 프론트엔드에는 "보고서 실패: " 라는 문자열이 존재하지 않는다. 새 코드는 "작업 등록 실패: " 또는 "작업 실패: " 를 쓴다. 즉 브라우저가 실행하고 있는 JS 는 예전 버전이다.
단서 2 — “Not Found”. 이건 FastAPI 가 등록되지 않은 경로에 대해 돌려주는 기본 404 본문 {"detail":"Not Found"} 의 detail 값이다. 앱이 만든 메시지가 아니다.
Trace

문자열을 따라가면 코드가 나온다

예전 app.js 의 handleReportResult() 는 응답 본문에서 message 가 없으면 detail 을 그대로 출력한다.

// 예전 webui/app.js — handleReportResult()
const msg = (r && (r.message || r.detail)) ||
            (r && r.errors && r.errors[0] && r.errors[0].message) ||
            (r && r.status) || "실패";
setStatus("보고서 실패: " + msg, "err", 7000);
//            ↑ 이 접두사 + FastAPI 의 detail:"Not Found" = "보고서 실패: Not Found"

그리고 예전 app.js 는 이 경로로 POST 한다. 새 서버에는 그 경로가 없었다.

$ 라우트 확인 (수정 전)
  /api/report                없음  <-- 404 원인
  /api/scene-report          없음  <-- 404 원인
  /api/jobs/report           있음
  /api/jobs/scene-report     있음
Root cause

원인 — 두 실수가 겹쳤다

  1. 구 라우트를 제거했다. 작업 큐를 도입하면서 /api/report, /api/scene-report 를 /api/jobs/* 로 교체했다. 새 server.py 의 docstring 에는 “호환 래퍼로 남긴다”고 써놓고 실제로는 구현하지 않았다. 문서와 코드가 어긋난 채로 넘어갔다.
  2. 정적 파일에 캐시 무효화 장치가 없었다. index.html 이 /webui/app.js 를 버전 파라미터 없이 참조해, 브라우저가 예전 사본을 계속 쓸 수 있었다. 서버만 새 코드로 바뀌고 프론트는 옛 코드인 상태가 만들어진다.
한 줄 요약
새 서버 + 캐시된 옛 프론트 = 존재하지 않는 경로로 POST → FastAPI 기본 404 → 옛 코드가 detail 을 그대로 출력.

왜 조합에 따라 메시지가 달라지는가

서버브라우저 JSPOST 대상결과
새(큐)옛(캐시)/api/report보고서 실패: Not Found ← 실제 발생
옛새/api/jobs/report작업 등록 실패: Not Found

Red herring

“캡처 6장”은 원인이 아니다

숫자 6이 설정값 max_analyze_images = 6 과 같아 관련을 의심하기 쉽다.

🔢 6은 우연이다

404 는 요청이 서버 라우팅에서 거부된 것이다. 본문(files 배열)은 읽히지도 않는다. 캡처 0장이든 20장이든 같은 404 가 난다.

📎 상한은 별개 동작

max_analyze_images 초과분은 오류가 아니라 분석에서 제외될 뿐이다. 이번 수정에서 그 초과분이 보고서 갤러리에도 실리지 않도록 함께 고쳤다 (“보지 않은 사진이 근거로 제시되는” 문제).

Fix 1

수정 1 — 구 라우트 복원 (큐 경유)

경로만 되살리는 게 아니라, 같은 작업 큐를 지나되 완료까지 기다렸다가 예전과 같은 모양의 JSON 을 돌려준다. 순차 처리 보장은 그대로 유지된다.

# src/geoguesshelper/server.py
async def _run_sync(kind: str, payload: dict, label: str):
    job = await _submit(kind, payload, label)      # 큐에 등록
    done = await _QUEUE.wait(job.id)               # 완료까지 대기
    if done.status == jobs.DONE:
        return JSONResponse(done.result or {})
    # 실패/취소도 예전처럼 200 + status 필드로 (옛 프론트가 그렇게 읽는다)
    body = dict(done.result or {})
    body.setdefault("status", "FAIL" if done.status == jobs.FAILED else "CANCELED")
    body["message"] = done.error or body.get("message") or "작업 실패"
    body["jobId"] = done.id
    return JSONResponse(body)

@app.post("/api/report")          # 복원
@app.post("/api/scene-report")    # 복원

대기를 위해 jobs.py 에 JobQueue.wait() 를 추가했다. Job 마다 asyncio.Event 를 두고 종료 시점에 set 한다 — 폴링이 아니다.

부수 효과. CLI·스크립트·다른 도구가 구 API 를 쓰고 있어도 이제 동작하며, 그것들도 자동으로 큐의 순차 처리 보호를 받는다.
Fix 2

수정 2 — 정적 파일 캐시 무효화

근본은 이쪽이다. 호환 라우트가 없었어도 프론트가 최신이면 문제가 없었다.

<!-- src/geoguesshelper/webui/index.html -->
<!-- ?v= 는 캐시 무효화용. 프론트를 고칠 때마다 올린다 -->
<link rel="stylesheet" href="/webui/styles.css?v=0.2.0">
<script src="/webui/app.js?v=0.2.0"></script>
사용자 조치 1회 필요. ?v= 가 붙기 이전의 index.html 자체가 캐시돼 있을 수 있다. 브라우저에서 Ctrl+Shift+R(강제 새로고침) 한 번이 필요하다. 그 이후로는 ?v= 값만 올리면 자동으로 갱신된다.
Verification

검증

$ 옛 경로 POST /api/report  (404 였던 것)
  status : FAIL
  message: 분석할 캡처 이미지가 없습니다.      # ← 앱이 만든 진짜 메시지
  jobId  : job_f10ee8e4db8d
 HTTP 200

$ 옛 경로 POST /api/scene-report
  HTTP 200

$ 큐를 실제로 지나갔는가
  큐 통계: {'queued': 0, 'running': 0, 'failed': 2, 'concurrency': 1, 'maxPending': 64}
   job_e25c1ff6f3c2 FAILED   바로 보고서
   job_f10ee8e4db8d FAILED   보고서

$ 캐시 무효화된 정적 파일
  /webui/app.js?v=0.2.0        HTTP 200  45624 bytes
  /webui/styles.css?v=0.2.0    HTTP 200  16575 bytes
“FAILED” 는 정상이다. 존재하지 않는 캡처 파일로 테스트했기 때문이다. 중요한 건 404 가 아니라 200 으로 응답하고, 앱이 만든 구체적 메시지가 돌아오며, 작업이 큐에 기록됐다는 점이다.

Prevention

재발 방지

  • 프론트를 수정하면 ?v= 를 올린다. 현재 0.2.0. 이걸 빠뜨리면 정확히 같은 부류의 버그가 다시 난다.
  • 공개 API 경로는 지우지 말고 남긴다. 클라이언트(브라우저 캐시 포함)를 서버와 동시에 갱신할 수 없다. 경로를 옮길 때는 옛 경로를 새 구현으로 위임시키는 편이 항상 싸다.
  • docstring 에 쓴 약속은 구현과 함께 커밋한다. 이번 회귀의 직접 원인은 “호환 래퍼로 남긴다”고 적고 구현하지 않은 것이다. 문서가 코드보다 앞서 나가면 그 격차가 버그가 된다.
  • 404 는 “서버가 그 경로를 모른다”는 뜻으로 읽는다. 요청 본문·데이터 문제로 착각하면 (이번엔 “캡처 6장”) 엉뚱한 곳을 파게 된다. 라우트 목록을 먼저 찍어보는 것이 가장 빠르다.
진단이 빨랐던 이유. 화면에 뜬 문자열 "보고서 실패: " 가 새 코드에는 없고 옛 코드에만 있었다. 사용자에게 보이는 메시지를 코드베이스에서 유일하게 유지하면 “지금 돌고 있는 게 어느 버전인가”를 즉시 알 수 있다.
