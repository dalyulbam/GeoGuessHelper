오류 분석 · 서버 기동 불가 · 2026-08-10

ssl.create_default_context() 가 프로세스를 스스로 종료시킨다

서버가 배너 한 줄도 못 찍고 죽었다. stderr 에는 OPENSSL_Uplink(...): no OPENSSL_Applink 한 줄만 남았다. 결론부터 — 외부에서 죽이는 것이 아니라 프로세스가 스스로 ExitProcess(1) 을 호출한다. 다만 그 방아쇠는 외부(백신)가 환경변수로 심는다. 이 문서는 오진 과정까지 포함해 어떻게 특정했는지를 남긴다.

증상: 서버 기동 즉시 종료 · 종료 코드 1 트리거: SSLKEYLOGFILE (Avast 주입) 수정: tls.neutralize_keylog() 해결됨 — 우회 플래그 없이 기동
Symptom

증상

서버를 띄우면 stdout 에 아무것도 안 나오고 즉시 프로세스가 사라진다.

# python -m geoguesshelper.server
--- stdout ---
(비어 있음 — 배너조차 안 찍힘)
--- stderr ---
OPENSSL_Uplink(00007FFCDAFEAC60,08): no OPENSSL_Applink
--- alive? ---
exited
혼동 포인트. 이 프로젝트는 오늘(8/9~10) 정상적으로 캡처를 만든 이력이 있다 (captures/*.png 타임스탬프 21:03). 그래서 처음에는 "방금 한 코드 변경 때문"으로 의심하기 쉽다. 실제로는 변경 이전 커밋(HEAD)도 똑같이 죽는다 — 아래 오진 정정 참고.
Correction

먼저: 내가 처음 내린 진단은 틀렸다

기록으로 남기는 이유 — 같은 함정에 다시 빠지지 않기 위해서다.

✗ 최초 가설 (틀림)

C:\WINDOWS\system32\libcrypto.dll 이 Python 번들 OpenSSL 을 가려서 (DLL 검색 순서상 system32 가 앞) applink 없는 DLL 이 로드된다.

근거로 삼은 것: PATH 스캔에서 그 DLL 이 실제로 발견됨.

왜 틀렸나: 프로세스에 로드된 모듈을 EnumProcessModules 로 직접 열거해 보니 OpenSSL 계열 DLL 이 단 하나도 로드되지 않는다. 가릴 대상 자체가 없었다.

✓ 실제 원인

백신(Avast)이 프로세스 환경에 SSLKEYLOGFILE 을 주입하고, create_default_context() 가 그 값을 읽어 OpenSSL 에 FILE* 를 넘기려다 applink 부재로 자가 종료한다.

결정적 증거: 그 환경변수만 지우면 즉시 통과(exit 0).

"내 변경 탓인가"를 먼저 끊어낸 방법

추측 대신 변경 이전 코드를 그대로 실행했다. git worktree 로 HEAD 를 별도 디렉터리에 꺼내 같은 인터프리터로 띄웠고, 동일하게 죽었다. 이 시점에서 "기존 환경 문제"로 범위가 확정됐다.

# 변경 이전 커밋을 격리 실행
git worktree add $TEMP\geo_orig HEAD
# → ORIGINAL(HEAD) stderr:
OPENSSL_Uplink(00007FFCDAFEAC60,08): no OPENSSL_Applink
→ 원본도 즉시 종료. 코드 변경과 무관.
Instrumentation

계측: 정확히 어느 호출에서 죽는가

create_default_context() 를 구성하는 단계를 하나씩 따로 호출해 경계를 좁혔다.

  • 통과 ssl.SSLContext(PROTOCOL_TLS_CLIENT)
  • 통과 ssl.enum_certificates('ROOT')  CryptoAPI
  • 통과 ctx.set_default_verify_paths()  파일 경로 기반
  • 통과 ctx.load_default_certs()
  • 사망 ssl.create_default_context()
이 결과가 결정적이다. CA 번들 로드(load_default_certs)까지 전부 멀쩡히 통과한다. 그렇다면 create_default_context() 가 그 위에 추가로 하는 일이 범인이다. CPython 소스를 보면 그건 딱 한 가지다.
# Lib/ssl.py — create_default_context() 끝부분
    if context.verify_mode != CERT_NONE:
        context.load_default_certs(purpose)      # ← 여기까지는 통과했다
    # OpenSSL 1.1.1 keylog file
    if hasattr(context, 'keylog_filename'):
        keylogfile = os.environ.get('SSLKEYLOGFILE')      <-- 범인
        if keylogfile and not sys.flags.ignore_environment:
            context.keylog_filename = keylogfile

환경변수 확인

프로세스 : '\\.\aswMonFltProxy\3e7f7b040b43e88d'   ← asw = Avast 필터 드라이버
사용자   : ''
시스템   : ''   ← 영구 설정이 아니라 런타임 주입이다
주목. 사용자/시스템 환경변수에는 없고 프로세스 환경에만 있다. 즉 레지스트리에 박힌 설정이 아니라, Avast 가 감시 대상 프로세스를 띄울 때 동적으로 주입한다. 그래서 setx 로 지우거나 시스템 환경변수 화면을 뒤져도 찾을 수 없다.
Root cause

근본 원인 — 5단계 연쇄

  1. Avast 가 환경변수를 주입한다. HTTPS 트래픽을 복호화해 검사하려면 TLS 세션 키가 필요하다. SSLKEYLOGFILE 은 "세션 키를 이 경로에 적어라"는 표준 규약이고, Avast 는 그 경로로 자기 필터 드라이버 디바이스(\\.\aswMonFltProxy\...)를 지정한다.
  2. Python 이 그 값을 그대로 따른다. ssl.py:725 가 변수를 읽어 context.keylog_filename 에 세팅한다.
  3. CPython 이 FILE* 를 OpenSSL 에 넘긴다. _ssl.c 의 setter 가 그 경로를 C 런타임 fopen() 으로 열고, 그 FILE* 를 BIO_new_fp() 에 전달한다.
  4. OpenSSL 이 applink 을 찾는다. Windows 에서 OpenSSL 이 애플리케이션의 CRT FILE* 를 다루려면, 애플리케이션이 applink.c 를 컴파일해 넣어 OPENSSL_Applink 심볼을 노출해야 한다. python.exe 에는 그게 없다.
  5. OpenSSL 이 프로세스를 끝낸다. OPENSSL_Uplink() 가 applink 부재를 감지하고 메시지를 출력한 뒤 ExitProcess(1) 을 호출한다. 예외가 아니라 즉시 종료라 try/except 로 잡을 수 없다.

결론
외부 프로세스가 TerminateProcess 로 죽이는 것이 아니다. 프로세스가 스스로 종료한다. 다만 그 방아쇠는 외부(Avast)가 심는다.
Why here

왜 하필 이 조합에서만 터지는가

같은 Avast 를 쓰는 다른 프로그램은 멀쩡한데 이 Python 만 죽는 이유.

📦 정적 링크 Python

이 인터프리터는 uv 의 python-build-standalone 빌드다. OpenSSL 을 정적 링크하므로 libcrypto-*.dll 이 로드되지 않는다 (모듈 열거 결과 0개). 정적 OpenSSL 에도 uplink 스텁 테이블은 남아 있는데, python.exe 는 applink.c 를 넣지 않았다.

🩺 백신의 키로그 주입

Avast 웹 실드가 HTTPS 검사를 위해 SSLKEYLOGFILE 을 주입한다. 이 변수를 읽는 프로그램만 영향을 받는다. Python ssl 모듈은 읽는다.

🔗 둘이 만나야 터진다

동적 링크 Python(공식 배포판)은 applink 을 제공하는 DLL 을 쓰므로 안 죽는다. Avast 가 없으면 변수가 없어 안 죽는다. 정적 링크 Python + 백신 키로그 주입이 겹쳐야 재현된다.

파급 범위. 이 문제는 GeoGuessHelper 만의 것이 아니다. 이 PC 에서 ssl.create_default_context() 를 호출하는 모든 uv/standalone Python 프로그램이 같은 방식으로 죽는다 (requests, httpx, pip, aiohttp …). 앞으로 다른 프로젝트에서 같은 증상을 보면 이 문서를 먼저 확인할 것.
Fix

수정 — tls.neutralize_keylog()

ssl 을 건드리기 전에 프로세스 환경에서 그 변수를 제거한다. 시스템 설정은 손대지 않는다.

# src/geoguesshelper/tls.py
def neutralize_keylog() -> str | None:
    """SSLKEYLOGFILE 을 제거한다. 반환값은 제거한 값(없었으면 None)."""
    global _keylog_removed
    v = os.environ.pop("SSLKEYLOGFILE", None)
    if v:
        _keylog_removed = v
    return v

def system_ssl_context() -> ssl.SSLContext:
    neutralize_keylog()      # create_default_context 보다 반드시 먼저
    return ssl.create_default_context()

main() 에서도 가장 먼저 호출해 decide_tls() 이전에 확실히 제거되도록 했고, 제거했으면 시작 배너에 그 사실을 표시한다.

# src/geoguesshelper/server.py — main()
_safe_stdout()
neutralize_keylog()          # ssl 을 건드리기 전에 먼저
tls_mode = decide_tls()
...
# 배너
   SSLKEYLOGFILE: 제거함 (\\.\aswMonFltProxy\...) - 백신 TLS 감청 지시

지우는 것이 안전한 이유

  • 이 값은 기능 설정이 아니라 "TLS 세션 키를 이 디바이스로 흘려라"는 지시다. 앱 동작에 필요 없다.
  • 남겨두면 ANTHROPIC_API_KEY 가 오가는 연결의 세션 키까지 백신 드라이버로 나간다.
  • os.environ.pop 은 이 프로세스와 그 자식(Chromium 등)에만 적용된다. 레지스트리·시스템 환경변수·Avast 설정은 그대로다. 되돌리려면 서버를 끄면 된다.

수정 전에는 GEOHELPER_INSECURE_TLS=1 을 줘야만 기동했다. 그 플래그는 decide_tls() 가 system_ssl_context() 를 아예 호출하지 않도록 우회시켜 우연히 죽음을 피한 것이지, 원인을 고친 게 아니었다. 이제는 플래그 없이 뜬다.
배너의 "TLS 검증: 끔" 은 별개 사안이다. 이건 크래시가 아니라 정상 판정 결과다 — Avast 가 TLS 를 가로채면서 자기 CA 로 인증서를 재발급하는데, 그 CA 가 Python 신뢰 저장소에 없어 프로브가 실제로 실패한다. tls.py 가 원래 이 환경을 위해 설계된 폴백이다. 아래 "근본 해결"을 적용하면 검증: 켬 으로 바뀐다.
Permanent fix

근본 해결 옵션

앱 내 조치는 증상을 막는다. 아래는 원인 자체를 없애는 방법이며, 하면 TLS 검증도 함께 살아난다.

방법내용효과
Avast HTTPS 스캐닝 끄기
권장		 Avast → 설정 → 보호 → 핵심 보호 → 웹 실드 → HTTPS 스캐닝 사용 해제 변수 주입이 사라짐
+ TLS 검증 켬 으로 복구
예외 추가 Avast 예외 목록에 .venv\Scripts\python.exe 또는 프로젝트 경로 등록 이 프로그램만 주입 제외

단, 키로그 문제는 앱 조치로 커버

Security

보안 함의 — 크래시보다 이쪽이 중요할 수 있다

이 PC 의 모든 프로세스에서 TLS 세션 키가 백신으로 흘러간다. SSLKEYLOGFILE 을 존중하는 프로그램(Python, curl, Firefox, Chrome 계열 일부)은 자신이 맺는 모든 HTTPS 연결의 세션 키를 그 경로에 쓴다. 세션 키가 있으면 캡처된 트래픽을 사후에 완전히 복호화할 수 있다. 백신의 의도된 동작이지만, 무엇이 감청 가능한지는 알고 쓰는 편이 낫다.
  • 이 앱은 이제 제외된다. 프로세스 시작 시 변수를 제거하므로 Anthropic·Google 로 가는 연결의 세션 키는 흘러가지 않는다.
  • 다른 프로그램은 여전히 흘린다. 앱 단위 조치라 시스템 전체를 덮지 않는다. 전체를 막으려면 위 "근본 해결"의 HTTPS 스캐닝 해제가 필요하다.
  • 확인해 볼 것: 이 값이 Avast 가 심은 것이 맞는지 재확인 권장. asw 접두는 Avast Software 의 관례지만, 백신을 사칭하는 소프트웨어도 존재한다. Avast 를 종료한 상태에서 새 셸을 열어 $env:SSLKEYLOGFILE 이 사라지는지 보면 확실하다.
