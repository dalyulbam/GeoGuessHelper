한국어 탭에 영어가 남았다 — 밤 배치의 번역 실패

1. 한 줄 요약

다국어 보고서는 영어로 한 번 만들고 나머지 언어는 문자열만 번역하는데, 번역 청크가 일시 오류로 죽으면 설계상 원문(영어)이 그대로 남는다. v0.3.3 이 고친 것은 “실패를 조용히 넘기던 것”이다 — 작업 로그에는 경고가 찍히게 됐지만, 보고서 파일은 여전히 영어를 실은 채 저장됐다. 실패한 청크를 다시 시도하는 코드는 없었고, 밤에 9건을 연달아 돌리는 부하에서 그 구멍이 아홉 번 반복됐다.
분석·서술 영어(기준)→ 청크 분할 → 동시 번역→ 일부 청크 실패 (재시도 없음)→ 경고는 로그로→ 보고서엔 영어 그대로

3. 원인 — 설계는 옳았고, 복구가 없었다

언어마다 전부 재분석하던 시절의 비용·정합 문제를 해결한 것이 지금의 “영어 한 벌 + 문자열 번역” 구조다(translate.py 머리 주석). 이 구조 자체는 유지할 가치가 있다.

기준 언어 원칙 — 분석(비전)·리서치(웹 검색)·서술(스크립트)은 영어로 한 번만. ko/fr 는 harvest → 평평한 {id:text} → 번역 → splice 로 문자열만 바꾼다. 로직 값(좌표·신뢰도·enum)은 애초에 전송이 안 돼 번역이 망가뜨릴 수 없다.
실패 시 원문 유지 — translate_texts() 는 실패해도 원문을 돌려준다. “보고서는 반드시 만든다”는 예산 철학의 일부로, 의도된 동작이다. 문제는 그 앞 단계 — 실패한 호출을 다시 시도하지 않는다.
부하 정황 — 21:22~23:22 두 시간에 9건. 각 건이 분석+리서치+다국어 번역+서술 검증을 동시에(llm.gather) 돌린다. SDK 자체 재시도(max_retries=2)를 뚫고 실패가 표면화될 조건이다. 신고 파일(23:22, 배치 마지막)이 가장 심하게 이환된 것도 정황과 맞는다.

그 밤의 작업 로그는 서버 재시작으로 남아 있지 않아, 실패가 429(레이트리밋)였는지 스트림 마감(LLMTimeout)이었는지는 단정하지 않는다. 어느 쪽이든 일시 오류이고, 아래 수리에서 같은 텍스트가 전부 정상 번역된 것이 그 방증이다.

4. 왜 또 나갔나 — 병상일지만 고친 수리

retranslate.py 머리 주석: “번역이 통째로 실패해도 조용히 원문이 남는 버그가 있었다 (v0.3.3 에서 수정)”. 이 문장이 이번 재발의 지도다.

시점무엇을 했나무엇을 안 했나
v0.3.3실패를 stats 로 밖으로 — 작업 로그에 “⚠ 한국어 번역 일부 실패”가 찍히게 됨 실패한 청크의 재시도. 경고 후 영어를 실은 채 저장하는 것은 그대로.
260812그 시기에 이환된 보고서 5건을 retranslate.repair_file() 로 사후 수리(.bak 5개가 그 흔적) 수리 도구의 CLI 연결. 모듈로만 존재해 다음 사람이 손으로 불러야 했다.
260813 밤보고서 9건 생산로그의 경고를 본 사람이 없었다 — 새벽 배치였고, 산출물은 멀쩡해 보였다.
패턴 “실패를 알린다”는 복구가 아니다. 알림의 수신자가 없는 시간대(밤 배치)에는 알림 채널(작업 로그)이 곧 침묵이다. 일시 오류는 그 자리에서 다시 시도하는 것만이 산출물을 지킨다 — 사람이 아니라 코드가 수신자여야 한다.

5. 고친 방식

재발 방지(재시도) · 복구 수단(CLI) · 현재 병소의 수리(전수 실행), 세 겹.

①실패 청크만 1회 재시도

translate_texts() 가 1차 결과에서 실패한 청크만 모아 3초 뒤 순차로(동시성 1) 다시 보낸다. 동시성을 줄여야 같은 제한에 재차 걸리지 않는다. 재시도 횟수는 stats["retried"] 로 남긴다.

②수리 도구를 CLI 로

uv run geoguesshelper retranslate <파일|폴더> -l ko [--dry-run]. --dry-run 은 API 호출 없이 미번역 노드 수만 센다. 원본은 .bak 으로 보존. README 에 문서화.

③이환분 전수 수리

9건에 ko(stikovica 는 ko+fr) 수리 실행. 치환 1,225곳, 비용 $1.168. 치환은 텍스트 노드만 — base64 이미지·속성·구조는 손대지 않는다.

7. 남은 것 — 숨기지 않는다

  • 라틴 문자 언어의 이환은 자동으로 못 잡는다. retranslate._HAS 는 ko/ja/zh 만 문자 클래스로 판정한다. fr/de/es 문서에 영어가 남아도 collect 는 전부를 “미번역 후보”로 세므로 신호가 없다 — stikovica 의 fr 이환은 표지어( the ) 밀도라는 임시 계측으로 찾았다. 언어 판별 휴리스틱(불용어 프로필)이 다음 후보다.
  • 재시도는 1회, 백오프는 3초 고정이다. 지속적 제한(수 분 단위 429)은 못 넘는다. 큐 수준의 배치 간 간격 조절은 없다.
  • 번역이 끝내 실패한 채 저장되는 보고서는 지금도 겉으로 표가 안 난다. langbar 나 해당 탭에 “이 언어는 일부 원문(영어)입니다” 배지를 다는 것이 정직하다 — 미구현.
  • 보고서 생성 직후 산출물 자체를 스캔(한글 부재 검사)해서 즉시 retranslate 를 물리는 자동 복구 고리도 가능하다 — 이번에는 도구와 수순만 만들었고 자동화하지 않았다.
  • 수리 비용 $1.168 은 번역 모델(model_fact = Sonnet) 기준. 원 생성 시 정상 번역됐다면 들지 않았을 돈이다 — 재시도 1회의 값이 이보다 싸다.
이번에 코드로 굳힌 규칙. 일시 오류의 1차 수신자는 사람이 아니라 코드다. 실패를 로그로 알리는 것은 진단이지 치료가 아니다 — 산출물에 실리는 값은 실패 지점에서 즉시, 조건을 바꿔(순차·지연) 한 번 더 시도한 뒤의 값이어야 한다. 그리고 사후 수리 도구는 CLI 가 있어야 도구다 — 모듈로만 있는 수리는 다음 사람에게 없는 것과 같다.
