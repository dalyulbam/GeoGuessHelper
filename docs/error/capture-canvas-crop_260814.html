260814 · v0.5.0 작업 트리

캡처가 화면보다 좁았다 — 4:3 에 갇힌 캔버스

사용자 질문: “현재 화면 캡처에 class="viewer" 사이즈의 캔버스 전체가 들어가나? 아니면 또 여기서 조금 잘리나?” 답은 잘린다였다. 캡처는 화면을 찍는 것이 아니라 서버가 640×480 고정(4:3) 으로 다시 그리는 것인데, 화면 로드뷰 패널은 창을 따라가는 가변 비율(와이드 모니터에서 2.7:1 안팎)이다. 세로 시야는 같았지만 화면 좌우 36° 어치가 캡처에 없었다 — 가장자리에 걸친 표지판은 보고서에 실리지 않았다.

증상: 캡처·보고서 이미지 좌우 상실 결함 3경로 + 축 오류 1건 app.js · capture.py · streetview.py · render_google.py 화면 종횡비 동봉으로 수리

1. 한 줄 요약

클라이언트는 화면 패널의 크기를 서버에 알려준 적이 없다. 캡처 포즈에는 heading/pitch/fov 만 실렸고, 서버의 세 렌더 경로(photo_url · static · playwright)는 전부 settings.viewport_w×viewport_h(640×480) 를 그렸다. 화면 패널 #pano 는 “창 너비 − 384px” × “뷰어 높이의 56%” 라 비율이 매번 다른데도. 게다가 static 경로는 수직 FOV 를 수평 FOV 자리에 그대로 넣어 그보다도 좁았다.
화면 ~2.67:1 · 수평 127.9°→ photo_url 4:3 → 91.3° static fov=75 그대로 → 75° playwright 640×480 → 91.3°

잘리는 것의 성격이 픽셀 크롭이 아니라 시야각 차이라는 점이 이 결함을 오래 살렸다. 중심(heading/pitch)과 세로 범위는 정확히 맞으므로 캡처는 언제나 “그럴듯한” 이미지였다. 틀린 것은 화면 가장자리 — 지오게서 복기에서 단서가 가장 자주 걸쳐 있는 곳이다.

2. 기하 — 얼마나 잘렸나

수직 FOV 75°(구글맵 URL 75y 기본), 1920px 창 기준 패널 1520×570(비율 2.667) 가정. 수평 FOV = 2·atan(비율·tan(수직/2)).

표면크기·비율수평 FOV화면 대비
화면 #pano 패널1520×570 · 2.67:1127.9°기준
photo_url 캡처 (제3자 파노)1280×960 · 4:391.3°−36.6° (좌우 각 ~18°)
playwright 캡처 (브라우저 렌더)640×480 · 4:3~91.3°−36.6°
static 캡처 (공식 파노)640×480 · 4:3, fov=7575°−52.9° — 필요한 것의 59%
static 이 가장 나빴던 이유는 축 오류다. 이 프로젝트의 pose["fov"] 는 수직 FOV 규약(75y)인데, Street View Static API 의 fov 파라미터는 수평 FOV 다(공식 문서 서술). 수직값 75 를 수평 자리에 그대로 넣으니 비율과 무관하게 수평 75° 만 담겼다. 같은 실수를 이미 한 번 했다 — lh3 의 -fo 도 수평인데 수직값을 넣어 좁게 잘렸고, v0.3.x 에서 photo_url 경로만 고쳤다. 실측 근거(그 링크는 75y·비율 1.5 → 변환 98.0°, 같은 URL 의 -fo 가 100)는 capture.photo_url_for 주석에 남아 있다. static 경로는 그때 함께 의심하지 않았다.

3. 경로별 해부

캡처는 브라우저 캔버스를 읽을 수 없어(교차출처 타일로 tainted) 전량 서버 재렌더다. 재렌더라는 설계는 옳다 — 문제는 재렌더의 프레임이 화면과 무관했다는 것.

경로수정 전무엇이 틀렸나
photo_url
제3자 파노 · lh3 직접 이미지		 w=1280, h=960 고정.
-fo 는 w/h 비율로 계산(옳음)		 수직 FOV·중심은 화면과 일치. 비율만 4:3 이라 좌우가 잘림.
static
공식 파노 · Static API		 size=640x480 고정.
fov=pose["fov"] 그대로		 비율 고정 + 수직값을 수평 자리에. 이중으로 좁음.
playwright
헤드리스 Chromium		 뷰포트 640×(480+260) 고정, zoom 은 화면 값 같은 SDK·같은 zoom 이지만 비율이 달라 프레이밍이 다름.

셋의 공통 원인은 하나다: 화면 패널 크기가 포즈에 없다. livePose() 는 시점(heading/pitch/fov/zoom)은 성실히 읽으면서 프레임은 읽지 않았다. 서버는 알 방법이 없으니 설정 기본값을 그렸다 — 640×480 은 이 앱의 화면 어디에도 없는 비율인데도.

4. 왜 지금까지 몰랐나

260813 기록(얼어붙은 거울)에서 “산출물을 재지 않는 스위트는 도구의 동작을 증명하지 않는다”는 규칙을 굳혔다. 그런데 그 규칙을 절반만 적용했다.

스위트(⑥ 캡처)가 재는 것이번 결함
이동 전후 캡처의 바이트가 달라지는가정상이었다 — 잘려도 바이트는 다르다.
캡처 좌표가 화면 좌표와 80m 이내인가정상이었다 — 중심은 늘 맞았다.
화각 — 캡처의 시야가 화면의 시야인가재지 않았다.
패턴 중심이 맞는 산출물은 검사를 통과하고, 가장자리가 틀린 산출물은 아무도 신고하지 않는다. 단서가 화면 끝에 걸렸을 때만 보고서가 조용히 부실해진다 — 그리고 그건 “분석이 약하다”로 보이지 “캡처가 좁다”로 보이지 않는다.

결국 이것을 드러낸 것은 계측이 아니라 사용자의 질문이었다 — “또 여기서 조금 잘리나?” 라는 “또” 에는 이 도구의 잘림 전력(lh3 -fo 축 오류)이 들어 있다. 같은 종류의 의심을 코드가 스스로 하지 못했다.

5. 고친 방식

원칙: 보고서에 들어가는 이미지는 화면 캔버스 전체를 담는다. 재렌더는 패널과 일치한다.

①패널 크기를 포즈에 동봉

paneSize() 가 캡처 시점에 #pano 의 실측(clientWidth/Height)을 재서 viewW/viewH 로 livePose() 에 싣는다. 수동 캡처와 “바로 보고서” 둘 다 이 경로를 지난다.

②비율 계산은 한 곳에서

streetview.view_aspect(pose, settings) 가 유일한 판정점. 값이 없거나 오염이면(구 클라이언트·API 직접 호출) 기존 4:3 으로 물러선다 — 새 필드가 없어도 예전보다 나빠지는 경로는 없다.

③photo_url — 비율만 맞추면 끝

h=960 기준으로 w=round(h·aspect)(상한 2048, 비율 유지 축소). -fo 는 원래 w/h 에서 계산했으므로 비율이 맞는 순간 수직·수평 시야가 화면과 정확히 일치한다.

④playwright — 같은 SDK·같은 비율·같은 zoom

렌더 뷰포트 폭을 round(480·aspect)(320~1600) 로. 화면과 같은 StreetViewPanorama 를 같은 비율·같은 zoom 으로 돌리므로 프레이밍이 화면과 같다. 검은 화면 판정(_top_is_black)의 상/하단 절단선도 새 높이 비율을 따른다.

⑤static — 축을 바로잡고, 한계는 말한다

640×640 상한 안에서 비율을 맞추고, 수직→수평 변환값을 fov 로 보낸다. 수평 120° 상한을 넘는 화면은 Static 으로 못 담는다 — 그때는 결과에 fov_capped(필요했던 각도)를 실어 상태 표시줄이 “화면(127.9°)보다 좁게 담김”을 말한다.

⑥auto — 전체를 담을 수 있는 쪽 먼저

필요 수평 FOV > 120° 이고 playwright 가 가용하면(키+설치) 브라우저 렌더를 먼저 시도하고, 실패 시 static 으로 계속한다. 이미 시도한 playwright 로는 재폴백하지 않는다. photo_url 우선순위는 그대로다.

7. 남은 것 — 숨기지 않는다

  • Static API fov=수평은 공식 문서 서술이지 이 저장소의 실측이 아니다. lh3 -fo 는 실측으로 확정했지만 Static 쪽은 아직이다. 만약 문서와 달리 다른 축이라면 static 캡처가 이번에는 화면보다 넓게 나올 수 있다 — 잘림보다는 낫지만, 실측으로 못 박아야 한다.
  • playwright 의 “같은 비율·같은 zoom → 같은 프레이밍”은 SDK 내부 규약에 대한 가정이다. 합리적이지만, 화면 스크린샷과 캡처 파일의 픽셀 대조는 아직 안 돌렸다.
  • 스위트는 여전히 화각을 재지 않는다. viewer_matrix.py ⑥ 은 바이트 차이와 좌표만 본다. 화면 #pano 스크린샷과 캡처 상단의 구조 유사도(가장자리 물체 유무) 항목이 다음 후보다.
  • WebGL 없는 <img> 폴백 경로의 화각 문제(260813 기록의 미해결 항목)는 이번에도 그대로다.
  • 와이드 화면에서 playwright 우선은 캡처가 수 초 느려진다. 정합을 속도보다 앞세운 선택이고, 급하면 캡처 방식을 static 으로 바꾸면 된다(그 경우 120° 상한 잘림을 감수).
이번에 코드로 굳힌 규칙. 산출물의 프레임은 화면에서 온다. 시점(heading/pitch/fov)만 화면에서 읽는 것으로는 부족하다 — 비율이 다르면 같은 시점도 다른 장면이다. 렌더 표면을 추가하거든 view_aspect() 를 지나는지부터 확인할 것.
