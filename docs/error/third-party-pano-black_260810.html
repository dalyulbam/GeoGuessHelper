제3자 로드뷰 검은 화면 — 타일은 429, 같은 토큰의 photo 형식은 200

사용자 기여(제3자) 파노가 뷰어에서 완전히 검게 나오는 문제. 원인은 이미지 CDN 의 IP 단위 레이트리밋이었고, 해결의 열쇠는 막힌 요청 그 자체였다 — 429 를 받은 요청에도 이미지 토큰은 URL 에 그대로 남아 있고, 같은 토큰의 다른 형식은 제한을 받지 않는다.

1. 증상

구글 지도 링크로 연 로드뷰 중 일부가 완전한 검정으로 표시된다. 오류 메시지도, 로딩 표시도 없다. 포즈 카드에는 좌표와 파노 ID 가 정상적으로 찍히고, 하단 지도도 정상이다.

사용자 보고 — “Geogrupa Pula 에서 아무리 봐도 이미지가 안 나오는데 너는 나오는가?” 같은 링크가 사람마다 다르게 보인다는 점이 첫 번째 단서였다. 콘텐츠 문제라면 누구에게나 똑같이 안 보여야 한다. 보는 쪽(IP)에 따라 갈린다면 그건 제한이다.

2. 틀렸던 가설들

가설근거로 삼은 것어떻게 깨졌나
이미지 형식·비율·해상도·확장자 문제검은 화면이라는 증상만 보고 추정 같은 파노가 어떤 실행에서는 정상 렌더(밝기 118.9). 콘텐츠가 원인이면 항상 실패해야 한다.
타일 요청 자체가 아예 없다계측에서 타일 요청 0건으로 측정 내 계측이 틀렸다. content-type: image 인 응답만 세고 있었다. 429 응답은 text/plain 이라 필터에 걸려 통째로 사라졌다.
파노 ID 형식으로 제3자를 판별할 수 있다CAoS/AF1Qip 접두, 22자 official 패턴 반례: ApCZpYJ184e4gUYfXHl65g 는 22자 official 형식인데 저작권은 © 2026 Google, CIHM0ogKEICAgIDaqcr9Gw 는 22자 패턴에 걸려 official 로 오분류됐다. 저작권 문자열만이 판별자다.
검으면 근처 공식 파노로 갈아탄다화면이라도 나오게 하려는 임시방편 이게 더 나쁘다. 요청한 곳이 아닌 다른 장소를 조용히 분석하게 된다. 지오게서 복기 도구에서 이건 오답을 정답처럼 만드는 일이다.
교훈 — “요청이 0건”이라는 관측은 사실이 아니라 내 필터를 통과한 것이 0건이라는 뜻이었다. 계측이 음성일 때는 계측 자체를 먼저 의심하고, 필터를 전부 벗긴 채 다시 재야 한다. 그렇게 하자 lh3.googleusercontent.com HTTP 429 가 바로 드러났다.

3. 결정적 관측

파노 타일의 출처는 두 갈래다.

구분호스트키제한
구글 공식 파노streetviewpixels-pa.googleapis.comAPI 키 기반없음(HTTP 200)
사용자 기여 파노lh3.googleusercontent.com/gpms-cs-s/<토큰>없음IP 단위 → HTTP 429

그리고 여기서 결정적인 사실이 나왔다. 같은 토큰이라도 URL 접미사에 따라 제한이 다르다:

<토큰>=x0-y0-z2-...                                 ← 타일 형식   HTTP 429
<토큰>=w1280-h800-k-no-pi0-ya0-ro0-fo90             ← photo 형식  HTTP 200

타일이 막힌 바로 그 순간 photo 형식은 1280×800 JPEG 218,670바이트, 밝기 118.9 로 정상 수신됐다. 즉 이미지는 받을 수 있는데 뷰어가 쓰는 경로만 막혀 있었던 것이다.

열쇠 — 429 로 거절당한 요청에도 URL 은 남는다. 거절은 응답의 성질이지 요청의 소멸이 아니다. 그러므로 막힌 요청에서 토큰을 줍고, 제한받지 않는 형식으로 다시 요청하면 된다. 우회가 아니라 같은 자원의 다른 표현을 쓰는 것이다.

4. “타일이 안 왔다”를 브라우저에서 어떻게 아는가

첫 시도는 PerformanceObserver 로 gpms-cs-s 요청을 관찰하는 것이었다. 실패했다.

타일 응답 1건 [429]   ← Playwright(CDP)에서는 보인다
perfCount : 0         ← 페이지 안에서는 한 건도 안 보인다

Maps JS API 가 파노 타일을 워커에서 받기 때문이다. 워커의 resource 엔트리는 그 워커의 타임라인에 쌓이고 문서 타임라인에는 오지 않는다. 요청을 볼 수 없다면 결과를 봐야 한다.

캔버스 오염(taint)을 신호로 쓴다
· 타일이 한 장이라도 그려졌다 → 교차출처 이미지가 들어갔다 → getImageData 가 SecurityError
· 타일이 한 장도 못 왔다 → 오염될 일이 없다 → 픽셀을 읽을 수 있고, 그 값은 검다
즉 “읽히는데 검다” = “타일이 안 왔다”. 타이밍 추정이 아니라 화면 그 자체를 근거로 삼는다.
function tilesMissing() {
  const cv = document.querySelector("#pano canvas");
  if (!cv || !cv.width) return false;
  try {
    const s = 24, c = document.createElement("canvas");
    c.width = s; c.height = s;
    const g = c.getContext("2d");
    g.drawImage(cv, 0, 0, s, s);
    const d = g.getImageData(0, 0, s, s).data;   // 오염됐으면 여기서 던진다
    let sum = 0;
    for (let i = 0; i < d.length; i += 4) sum += (d[i] + d[i+1] + d[i+2]) / 3;
    return sum / (d.length / 4) < 8;             // 사실상 완전한 검정
  } catch (e) {
    return false;                                 // 오염됨 = 타일이 왔다 = 정상
  }
}

실측으로 확인한 값: 캔버스 3개 모두 read=ok mean=0.0 — 읽히고, 검다.

5. 토큰은 서버만 알아낼 수 있다

감지는 페이지에서 되지만 토큰은 페이지에서 얻을 수 없다. 같은 이유다 — 요청이 워커에 있다. 반면 Playwright 는 CDP 로 브라우저 전체의 요청을 보므로 워커 요청도 그대로 보인다. 그래서 GET /api/pano-photo?pano=... 를 만들었다: 헤드리스로 그 파노를 한 번 열고, 나가는 gpms-cs-s 요청 URL 에서 토큰만 줍는다. 429 를 받아도 무방하다 — 필요한 건 URL 이지 응답이 아니다.

def _on_req(r):
    if "gpms-cs-s" in r.url and not found:
        m = _GPMS_RE.search(r.url)
        if m: found.append(m.group(1))
page.on("request", _on_req)

브라우저 기동이 비싸므로 파노당 한 번만 조회하고 캐시한다. 실측 콜드 9.4초, 캐시 히트 0.13초.

7. 실측

재현 자체가 한 번 더 함정이었다. page.route 로 타일을 429 로 바꾸자 타일 요청이 통째로 사라졌다(정상 조건 15건 → 개입 시 0건). 워커 요청은 page 라우트로 잡히지 않아 요청이 죽어버린 것이다. context.route 로 바꾸자 “429 를 받는” 상태가 정확히 재현됐다.
