브라우저에서 임계를 돌려 본 결과는 저장되지 않는다. 기록은 서버 빌드가 만든 스냅샷만이다. 화면은 미리보기를 점선 헐로, 기록된 스냅샷을 실선 헐로 구분한다 — 두 개가 다르면 "이 pct 로 build 를 돌려라"는 명령어를 복사해 준다.

🧭아틀라스와의 관계

  • 아틀라스: 좌표 · 행위자 · 관계 · 시대 · 강역 — "어디에, 누가, 언제".
  • 관측소: 수 · 변화 · 결손 · 근접 · 분자 — "얼마나, 어떻게 변하는가, 무엇과 가까운가".
  • 연결은 원자 id 와 좌표 두 가지뿐: 관측소 원자 행의 "지도에서" → index.html#atom=atm_…(flyTo), 아틀라스 원자 패널의 "관측소에서" → observe.html#atom=atm_….
  • 관측소는 data/entities.json·relations.json·periods.json 을 읽지 않는다. 아틀라스 사이드카가 비어도 관측소는 전부 뜬다.

📦배포와 동기화

  • sync-knowledge.ps1 의 제외 목록에 embeddings.npz(4MB, 뷰어 불필요)와 baseline/store_*(실험 샌드박스)를 더한다. observe/*.json·molecule/*.md·baseline/tiers.json 은 싣는다.
  • observe build 는 시스템 파이썬(numpy·torch 가 있는 쪽)에서 돈다 — 분자 파이프라인과 같은 제약. 그래서 CLI 한 명령으로 묶지 못하고(uv 가상환경 ↔ 시스템 파이썬을 오가야 한다) 셸 스크립트가 필요하다: 본체 루트의 snapshot-knowledge.ps1(run.ps1 옆) 이 embed → molecule build → observe build → altaiya\sync-knowledge.ps1 을 잇는다.
  • 이름이 snapshot- 인 이유: 이 스크립트는 원자(지식)를 갱신하지 않는다 — 원자는 적재(ingest)가 만든다. 하는 일은 그 시점의 원자 집합을 세 겹의 스냅샷으로 고정하는 것이다: 분자 스냅샷(molecule/snapshots/) · 관측 스냅샷(observe/series.jsonl 한 줄) · 배포 스냅샷(altaiya/knowledge/). 초안의 refresh-knowledge 는 "지식을 새로 고친다"로 읽혀 틀린 이름이었다.
  • 로컬(모노리포)에서는 사이드카가 없어도 observe.html 이 index.json 만으로 ①②를 띄우고, ③④는 "빌드 필요" 안내를 낸다 — 단계적 저하.

내장인가, 별도인가 — 프로세스는 내장, 화면·코드·데이터는 별도

원자 대장·계기판·분자 서가는 한 페이지의 탭 셋이고(임베딩 지도·작업대까지 다섯), 그 페이지는 altaiya 서버가 낸다. 그러나 아틀라스 지도와 파일 하나도 공유하지 않는다. 층별로 나누면 다음과 같다.

분자 관측의 특수성

분자는 시점의 함수다 — 그래서 "같은 분자"부터 정의해야 한다

🧬계보(lineage) 규칙

  • persist — 같은 id(내용 주소 = 같은 멤버 집합). 이론 §2.2 의 "id 로 셀 수 있다".
  • continue — id 가 달라졌지만 이전 스냅샷의 어느 분자와 자카드 ≥ 0.5. 멤버가 하나 들고 나간 경우. 계보 이름은 첫 분자의 것을 물려받는다(문서는 새로 안 쓴다 — 명명은 사람이 시킬 때만).
  • born / dissolved — 한쪽에만. dissolved 는 문서를 지우지 않는다(같은 구성이 돌아오면 같은 id 로 이어진다).
  • merged / split — 다대일·일대다. 이론 (f) 거대분자의 전조로 표시.

📏지속성(persistence) — 임계 하나를 믿지 않기

build --sweep 은 이미 pct 별 분자 수를 낸다. 관측 빌드는 여기서 한 걸음 더 — pct 0.25·0.5·1·2·3 각각의 분자 집합을 저장하고, 분자마다 어느 pct 에서 처음 생기고 어디서 깨지는지를 막대로 만든다. 넓은 막대는 임계에 강건한 개념, 0.5 에서만 사는 좁은 막대는 임계 인공물일 수 있다(이론 (b)). 명명 예산은 넓은 막대부터 쓰는 것이 옳다.

🎯near-miss 는 판별자다

분자 상세의 "주변 원자" 표는 흡수된 이웃 클리크에서 온 원자(현재 98개 클리크의 잔여)다. 관측 빌드는 여기에 멤버 전원과의 거리를 붙인다 — "이 원자는 4명 중 3명과 가깝고 1명과 0.41 로 멀다". 그 한 쌍이 D 를 배제한 이유이고, GeoGuessr 판별자로 쓰이는 "비슷하지만 다른 것"(이론 (g))이다. 대화 기획의 진입점 ③("두 원자는 같은 얘긴가")이 여기서 열린다.

📮환원(reification)은 예측 — 채점표

62개 문서의 missing_atoms 137줄은 "이 개념이 실재하면 이런 원자가 들어올 것이다"라는 예측이다. 작업대의 감시 목록이 links.jsonl 의 missing-atom-match 사건으로 채점된다. 지금 19건·분자 4개가 맞았다(단, 15건이 dalmatia 한 엔티티에 걸린 것이라 key 를 보여줘 넓은 매칭을 사람이 걸러낼 수 있게 한다).

스냅샷을 자주 만들어야 계보가 산다. 지금은 하나다. 원칙: P1·P2·P3 적재가 원자를 남긴 날은 그날 밤 embed → build → observe build 를 돈다(LLM 0, GPU 수십 초). 스냅샷 파일은 작다(120분자 ≈ 60KB). 이것을 snapshot-knowledge.ps1 로 한 번에 묶고, 신호 stale-snapshot 이 빠뜨린 날을 알려준다. (결정 2026-09-07: 이 주기로 간다 — 자동 스케줄러는 두지 않고, 적재를 돈 사람이 같은 자리에서 한 번 더 실행한다.)
