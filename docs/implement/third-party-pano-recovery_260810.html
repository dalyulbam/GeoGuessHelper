Step 3

전환점 — “직접 눈으로 확인하면 안 되는가”

사용자의 한 문장이 검증 층위를 바꿨다.

그때까지 나는 부품을 시험하고 있었다. 파노 하나를 따로 렌더하고, URL 하나를 따로 받아 보고, 객체 하나를 따로 들여다봤다. 사용자는 물건 자체를 보라고 했다.

왜 이게 중요한가. 부품 시험은 “타일 200 이 왔다” 같은 대리 지표를 준다. 그런데 사용자가 겪는 것은 지표가 아니라 화면이다. 200 이 와도 화면이 검을 수 있고, 429 가 나도 화면이 멀쩡할 수 있다(뒤에 둘 다 실제로 나온다). 검증은 사용자가 겪는 층에서 해야 한다.

그래서 첫 행동을 바꿨다. 이론을 더 세우는 대신, 앱의 캡처 경로를 지금 그대로 돌렸다.

Step 4 · 핵심

열쇠 — 거절은 요청을 지우지 않는다

두 개의 관찰이 부딪혀 하나의 가설이 됐다.

① 제한은 호스트 단위가 아니다

같은 lh3 호스트인데 타일은 429, photo 는 200. 그렇다면 제한의 단위는 호스트가 아니라 표현(형식)이다. 엔드포인트를 하나의 덩어리로 보면 안 된다.

② 429 는 응답의 성질이다

거절당했다는 것은 요청이 이미 나갔다는 뜻이다. 그리고 그 요청 URL 에는 토큰이 온전히 들어 있다. 실패한 시도가 남긴 잔해에도 정보가 있다.

가설. 막힌 요청에서 토큰을 줍고, 제한받지 않는 형식으로 다시 요청한다. 이건 우회가 아니라 같은 자원의 다른 표현을 쓰는 것이다.

실험을 어떻게 설계했나

  1. 반드시 429 가 나는 상태에서 잡는다. 정상일 때 잡으면 “타일이 되니까 photo 도 된다”는 동어반복이 된다. 실패 조건에서만 의미가 있다.
  2. 응답이 아니라 요청 단계에서 URL 을 수집한다. 응답 훅은 성공한 것만 주는 함정이 있다 (앞 문서에서 이미 한 번 당했다). 요청은 성패와 무관하게 관측된다.
  3. 받은 바이트를 눈으로 본다. 밝기 숫자는 “검지 않다”는 뜻일 뿐 “맞는 장면”이라는 뜻이 아니다.
# 요청 단계에서 URL 을 본다 — 응답이 429여도 URL 은 남는다
pg.on("request",  lambda r: seen.append(r.url) if "gpms-cs-s" in r.url else None)
pg.on("response", lambda r: codes.__setitem__(r.status, codes.get(r.status, 0) + 1)
                            if "gpms-cs-s" in r.url else None)

Step 6 · 가장 어려웠던 부분

라이브 뷰어 — 관측할 수 없는 것을 관측하기

서버는 CDP 로 다 본다. 그런데 사용자의 브라우저는 그럴 수 없다.

6.1 첫 시도: PerformanceObserver — 실패

계획은 단순했다. 페이지 안에서 gpms-cs-s 리소스 엔트리를 관찰하면 실패 여부와 토큰을 한 번에 얻는다. 서버 왕복이 필요 없다.

타일 응답 1건 [429]   ← Playwright(CDP) 에서는 보인다
perfCount : 0         ← 페이지 안에서는 한 건도 안 보인다
statuses  : []
원인. Maps JS API 는 파노 타일을 워커에서 받는다. 워커의 resource 엔트리는 그 워커의 타임라인에 쌓이고 문서 타임라인에는 오지 않는다. 이건 내 코드의 버그가 아니라 관측 지점의 한계다.

이 실패가 문제를 둘로 쪼개 줬다. 예전에는 한 방에 풀려던 것이 사실은 두 개였다.

A 실패를 아는 것

타일이 안 왔다는 것을 페이지가 스스로 알아야 한다.

B 토큰을 아는 것

그 파노의 gpms-cs-s 주소를 얻어야 한다.

둘을 분리하고 나니 각각 다른 해법이 보였다. 하나로 묶여 있는 동안에는 “페이지에서 요청을 볼 수 없다”가 양쪽 모두의 사형선고처럼 보였다.

6.2 A 의 해법: 캔버스 오염을 센서로 쓴다

요청을 볼 수 없으면 결과를 봐야 한다. 그런데 화면은 WebGL 캔버스이고, 교차출처 타일 때문에 오염(tainted)되어 읽을 수 없다 — 라고 알고 있었다. 실제로 캡처 모듈 주석에 그렇게 적혀 있다:

# 브라우저 캔버스는 WebGL + 교차출처 타일로 tainted 되어 toDataURL 이 SecurityError 를 던진다.
반전. 타일이 한 장도 안 왔다면 오염될 일도 없다. 그러면 읽을 수 있다는 사실 자체가 신호가 된다. 장애물을 센서로 뒤집어 쓴 것이다.

· 읽힌다 + 검다  →  타일이 안 왔다
· SecurityError 를 던진다  →  타일이 왔다 = 정상
function tilesMissing() {
  const cv = document.querySelector("#pano canvas");
  if (!cv || !cv.width) return false;
  try {
    const s = 24, c = document.createElement("canvas");
    c.width = s; c.height = s;
    const g = c.getContext("2d");
    g.drawImage(cv, 0, 0, s, s);
    const d = g.getImageData(0, 0, s, s).data;   // 오염됐으면 여기서 던진다
    let sum = 0;
    for (let i = 0; i < d.length; i += 4) sum += (d[i] + d[i+1] + d[i+2]) / 3;
    return sum / (d.length / 4) < 8;             // 사실상 완전한 검정
  } catch (e) {
    return false;                                 // 오염됨 = 타일이 왔다 = 정상
  }
}

왜 타이밍 규칙보다 나은가. “3초 기다렸는데 안 오면 실패” 같은 규칙은 느린 회선에서 오탐한다. 캔버스는 추정이 아니라 화면 그 자체다. 사용자가 보고 있는 것과 판정 근거가 정확히 같다.

6.3 B 의 해법: 토큰은 서버만 안다

같은 이유로 토큰도 페이지에서는 못 얻는다. 그런데 Playwright 는 CDP 로 브라우저 전체의 요청을 보므로 워커 요청도 그대로 보인다. 그래서 서버에 조회 창구를 냈다.

GET /api/pano-photo?pano=<파노 ID>   →   {"base": "https://lh3.../gpms-cs-s/AFP8Rc…"}
4절의 관찰이 여기서 다시 쓰인다. 이 조회는 429 를 받아도 무방하다 — 필요한 건 URL 이지 응답이 아니다. 그래서 “제한이 걸린 상태”에서도 항상 성공한다. 하나의 통찰이 서버·클라이언트 양쪽에서 각각 한 번씩 값을 했다.

브라우저 기동이 비싸므로 파노당 한 번만 조회하고 캐시한다. 실측 콜드 9.4초 / 캐시 히트 0.13초.

Step 7

조용히 삼켜진 실패들 — 시간이 버그를 신고한다

엔드포인트를 붙이자마자 null 이 돌아왔다. 그런데 너무 빨랐다.

증상

{"base":null,"reason":"not_found"} — 0.15초

관찰
real 0m0.155s. 그런데 이 엔드포인트는 Chromium 을 띄우고 Maps JS 를 로드한 뒤 5초를 기다린다. 아무리 빨라도 몇 초는 걸려야 한다.
질문
“못 찾았다”가 아니라 “시도조차 안 했다”가 아닌가?
원인
except Exception 이 예외를 먹고 None 을 캐시하고 있었다. 예외는 두 개였다:
· render_google 가 server.py 에 import 되어 있지 않았다 → NameError
· settings.render_settle_ms 라는 설정이 존재하지 않았다 → AttributeError
수정
지연 import 로 바꾸고, 존재하지 않던 설정은 상수로 대체했다. 그리고 삼키는 자리에 로그를 넣었다.
일반화 두 가지.
① except Exception 으로 폴백을 만들 때는 반드시 흔적을 남긴다. 조용한 폴백은 버그를 기능처럼 보이게 한다 — 이 엔드포인트는 “토큰을 못 찾는 파노”처럼 정상적으로 실패하고 있었다.
② 불가능한 소요 시간은 그 자체로 버그 신고다. 결과값이 그럴듯해도, 걸린 시간이 물리적으로 말이 안 되면 그 경로는 실행되지 않은 것이다. 앞 문서의 1181초 사례가 “너무 느림”이었다면 이번엔 “너무 빠름”이었다.

그리고 검증 자체의 거짓 음성 두 건

무엇을 봤나어떻게 오독했나실제
/api/pano-photo → 404 “라우트가 등록되지 않았다” 옛 서버가 살아 있어 _find_free_port 가 새 서버를 8802 로 밀었다. curl 은 옛 서버(8801)를 때리고 있었다.
curl /app.js | grep -c tilesMissing → 0 “낡은 JS 가 서빙된다” 실제 경로는 /webui/app.js. 그 경로로 재확인하니 2. 새 코드는 처음부터 정상 서빙되고 있었다.
같은 실수가 이 프로젝트에서 세 번째다. ① 앞 문서 — 호스트 패턴 필터가 lh3 를 걸러냄 ② 6.1 — 워커라서 PerformanceObserver 에 안 잡힘 ③ 여기 — 포트와 경로가 어긋남

전부 “0건/없음”을 사실로 받아들인 것이다. 그래서 규칙으로 굳혔다: 부정 결과를 보면 결론 내리기 전에 계측 경로부터 확인한다. 긍정 결과는 스스로를 증명하지만, 부정 결과는 그렇지 않다.
Step 8

경합 — pano_changed 는 한 번이 아니다

부품은 전부 정상인데 조립하면 실패하는 상태.

증상

자동 흐름만 실패한다

진단 방법
추측 대신 반쪽씩 갈랐다. 페이지 안에서 조각을 하나씩 직접 호출해 봤다.
전역 노출      : ['function', 'function', 'boolean']
tilesMissing() : True      ← 감지 로직 정상
gpmsBlocked    : True      ← 리스너가 자동으로 이미 설정했다
수동 호출 후   : {'fallback': 'ON', 'natW': 1056}   ← 표시 로직 정상
추론
감지도 되고, 리스너도 붙어 있고, 표시도 된다. 조각이 전부 정상이면 남는 것은 순서뿐이다.
원인
pano_changed 는 한 파노를 여는 동안에도 여러 번 튄다. 매 이벤트마다 clearFallback() 이 상태를 비웠고, 서버 토큰 조회(약 10초)가 돌아오는 사이에 그 결과가 지워졌다. 비동기 응답이 도착했을 때 그것을 받을 자리가 이미 없어진 것이다.
수정
상태를 파노 ID 에 못 박는다. 이벤트가 몇 번 오든, ID 가 실제로 바뀐 경우에만 버린다.
function watchTiles() {
  const id = pano && pano.getPano ? pano.getPano() : "";
  if (!id) return;
  if (id === watchedPano) return;          // 같은 파노를 두 번 감시하지 않는다
  watchedPano = id;
  ...
  api(`/api/pano-photo?pano=${encodeURIComponent(id)}`)
    .then((r) => {
      if (!r || !r.base || watchedPano !== id) return;   // 그새 이동했으면 버린다
      gpmsToken = r.base;

}
일반 규칙. 비동기 조회 결과를 되돌려 쓸 때는 요청 시점의 정체성을 함께 들고 다녀야 한다. “아직 유효한가”를 플래그로 판단하면 이벤트 순서에 지고, 정체성으로 판단하면 이긴다. 덤으로 이 구조는 안전성도 준다 — 사용자가 다른 파노로 이동한 뒤 늦게 도착한 이미지가 엉뚱한 장소를 덮어 그리는 일이 원천적으로 불가능해진다.
Step 9

재현 장치도 테스트 대상이다

고쳤는지 확인하려면 429 를 마음대로 만들 수 있어야 한다.

실제 429 는 언제 걸릴지 모른다. 그래서 타일만 429 로 바꾸고 photo 는 통과시키는 재현 장치를 만들었다. 관찰된 현실을 그대로 흉내 내는 것이 목표다.

def route(r):
    u = r.request.url
    if "gpms-cs-s" in u and "-k-no-pi" not in u:   # 타일만
        r.fulfill(status=429, content_type="text/plain", body="rate limited")
    else:
        r.continue_()
그런데

타일 요청이 통째로 사라졌다

관찰
개입하자 타일 요청이 0건. 심지어 하단 지도까지 안 떴다. 대조군(개입 없음)에서는 15건 · 전부 200.
질문
내가 만든 상태가 정말 “429 를 받는 상태”인가?
원인
워커 요청은 page.route 로 잡히지 않는다. 라우트를 걸자 그 요청들이 처리되지 못하고 죽었다. 즉 나는 재현하려던 상태가 아니라 전혀 다른 상태(요청이 소멸함)를 만들어 놓고 있었다. 6.1 에서 만난 워커 문제가 모습을 바꿔 다시 나타난 것이다.
수정
context.route 로 바꿨다. 컨텍스트 라우트는 워커 요청까지 잡는다.
타일 1건 [429]  ·  photo 1건 [200]
fallback : ON
natW     : 1056     natH : 450
이걸 어떻게 잡았나. 대조군을 먼저 재 뒀기 때문이다. “개입 없이 15건 200”이라는 기준선이 있었기에 “개입 시 0건”이 제한의 증거가 아니라 내 장치의 결함임을 알 수 있었다. 기준선이 없었다면 “역시 제3자는 요청 자체가 없다”는 앞 문서의 오판을 그대로 반복했을 것이다.
Step 10

측정이 대상을 오염시킨다

검증을 반복하다 검증 환경 자체가 망가졌다.

헤드리스를 계속 띄우다 보니 Maps JS API 가 아예 로드되지 않는 구간에 들어갔다. 로드뷰뿐 아니라 하단 지도까지 빈 화면이었다. 잔여 Chromium 프로세스로 MemoryError 도 났다.

이 구간의 측정은 전부 무효다. 여기서 나온 실패를 내 코드 탓으로 돌렸다면 존재하지 않는 버그를 몇 시간 쫓았을 것이다.

판별법: 정상 조건 대조군을 다시 돌린다. 개입이 없는데도 실패하면 환경 문제다. 실제로 그렇게 확인했다 — 라우트 개입을 빼고 돌리자 gpms 요청 15건 · 응답 {200: 15} 로 멀쩡했다. 그러면 범인은 내 코드가 아니라 재현 장치와 측정 부하다.

처치: 잔여 프로세스 정리 → 쿨다운 → 한 번에 한 실행. 그리고 판정은 한 번의 깨끗한 실행으로 한다. 흔들리는 환경에서 여러 번 돌려 평균 내는 것은 노이즈를 신호로 만드는 일이다.

Step 11 · 후속 신고

같은 “검은 화면”, 다른 원인 두 개

고친 뒤에 같은 증상이 또 왔다. 증상이 같다고 원인이 같지 않다.

사용자가 크로아티아 링크 두 개를 보내며 “추출하면 검은 화면”, “확실히 먹통”이라고 했다. 429 문제는 이미 고쳤으니 같은 원인일 리 없다 — 그래서 처음부터 다시 쟀다.

가설을 셋 세우고 셋 다 반증했다

가설측정결과
파노 ID 가 스테일이다ID 조회 vs 좌표 조회 비교 둘 다 OK, 같은 파노 — 반증
생성자의 암묵적 조회가 다른 파노를 고른다제약 없는 조회 vs OUTDOOR 조회 같은 파노 — 반증
컨테이너가 숨겨진 채 생성된다DOM/CSS 확인 #pano 는 숨겨지지 않는다 — 반증
그리고 내 측정이 또 한 번 나를 속였다. 헤디드(실제 GPU) 브라우저에서 캔버스를 읽으니 15초 내내 mean=0 이었다. “재현됐다”고 생각했다. 아니었다 — WebGL 은 preserveDrawingBuffer 가 기본 false 라, 합성이 끝난 뒤 캔버스를 읽으면 화면과 무관하게 검게 나온다. 헤드리스(SwiftShader)에서는 버퍼가 남아 있어 제대로 읽혔던 것뿐이다.

그래서 측정을 바꿨다. 캔버스를 읽지 않고 합성 결과(스크린샷)의 픽셀을 쟀다. 사용자가 보는 것이 바로 그것이기 때문이다.

헤드리스 캔버스 읽기      mean 117.2   ← 맞다
헤디드   캔버스 읽기      mean   0.0   ← 측정 인공물
헤디드   스크린샷 판정    mean 126.4   ← 진짜. 타일 15건 200. 정상 렌더
이 오측정이 오히려 회귀를 잡아 줬다. tilesMissing() 은 캔버스를 읽는다 — 즉 실제 GPU 브라우저에서는 공식 파노를 전부 “검다”고 오판한다. 제3자 파노는 CORS 가 없어 캔버스를 오염시키므로 판정이 성립하지만, 공식 파노는 CORS 가 열려 있어 읽히고 — 그리고 늘 검게 읽힌다. 결과는 파노마다 10초짜리 헤드리스 조회가 헛돌아가는 것이었다. 고쳤다: 저작권으로 제3자인 경우에만 감시한다. 실측 /api/pano-photo 호출 0회.

진짜 원인 — 스크린샷이 말해 줬다

사용자가 보낸 앱 화면에 답이 있었다. 우리가 만든 경고 배너가 정확히 잡아내고 있었다:

표시 중   CAoSFkNJ…Wnc.   © Gerd Rammelsberger   ← 화면에 있는 것
⚠ 링크의 파노(KKMPlm4X…FG2A)와 다릅니다

뷰어가 엉뚱한 제3자 사진구체를 들고 있었고, 그게 429 로 검었던 것이다. 두 번째 링크를 재 보니 원인이 드러났다.

CIHM0ogKEICAgIDqvbDfZw
    ID 조회   : ZERO_RESULTS
    좌표 조회 : ZERO_RESULTS
Maps JS API 는 이 파노를 아예 모른다. 사진구체(Photo Sphere)는 google.com/maps 본체만 서비스한다 — 사용자가 보낸 두 번째 스크린샷이 그 증거다(구글에서는 잘 보인다). 그런 ID 를 setPano() 에 넣으면 조용히 아무 일도 일어나지 않고, 뷰어는 직전 탭의 장면을 그대로 들고 있는다. 사용자에겐 “먹통” 또는 “엉뚱한 파노”로 보인다.

해결 — 답은 이미 링크 안에 있었다

그 링크에는 !6s 로 lh3 원본 이미지 주소가 들어 있었다. 캡처 경로는 이미 그걸 쓰고 있었는데 라이브 뷰어만 무시하고 있었다. 4절에서 만든 #pano-fallback 장치를 그대로 재사용하면 된다.

if (pose.pano) {
  armWhenLoaded(myToken, pose.pano, tabId);
  // 해석되는 파노인지 먼저 확인하고 나서 넘긴다
  svc.getPanorama({ pano: pose.pano })
    .then(() => { if (myToken === loadToken) pano.setPano(pose.pano); })
    .catch(() => { if (myToken === loadToken) panoUnavailable(pose, myToken, tabId); });
}

panoUnavailable() 은 세 단계로 물러선다 — ① 링크의 원본 이미지, ② 좌표 최근접(대체됐음을 반드시 알린다), ③ 그것도 없으면 명확히 말한다. 침묵하지 않는 것이 설계 원칙이다.

여기서 얻은 원칙. 증상이 같아도 원인은 다를 수 있다. “검은 로드뷰”는 하나의 버그가 아니라 세 개였다 — ⓐ 타일 429, ⓑ SDK 가 모르는 사진구체, ⓒ 엉뚱한 파노를 들고 있는 상태. 이미 고친 원인으로 새 신고를 설명하려 들면 가장 빠르게 틀리는 길이다. 그리고 새 원인을 찾아낸 것은 추론이 아니라 우리가 심어 둔 경고 배너였다 — 진단 장치를 제품에 남겨 두면 다음 버그를 사용자가 대신 찾아 준다.

왜 “우회 off” 행이 중요한가. 고친 것만 확인하면 절반이다. 고치지 말아야 할 것을 안 건드렸는지도 확인해야 한다. 정상 파노에서 우회가 켜졌다면 모든 파노를 정지 이미지로 바꿔 버렸을 것이다. 이 행이 그걸 막는다.

덤으로 잡은 버그 — 저작권이 한 번도 안 뜨던 이유

사용자 스크린샷에 저작권 칩이 없다는 것이 단서였다. 원인은 속성이 있는 자리를 잘못 안 것이다.

pano.getLocation()                    → StreetViewLocation      · copyright 없음
svc.getPanorama({pano}) 의 data       → StreetViewPanoramaData  · copyright 있음

이 때문에 판정값이 늘 빈 문자열이었고, 제3자 파노인데도 안내가 한 번도 뜨지 않았다. “조건문이 안 걸린다”가 아니라 “입력이 늘 비어 있었다”가 답이었다 — 분기 로직을 아무리 봐도 못 찾았을 종류의 버그다.

Method

방법론 — 이번에 실제로 쓴 것

원칙을 먼저 세운 게 아니라, 틀리면서 얻은 것을 뒤에 정리했다.

1

부정 결과는 스스로를 증명하지 않는다

“0건”은 세상에 대한 사실이 아니라 내 계측기를 통과한 것이 0건이라는 뜻이다. 이번 작업에서만 세 번 당했다 — 호스트 필터, 워커 타임라인, 포트/경로. 부정 결과를 보면 결론 전에 계측 경로부터 확인한다.

2

거절은 요청을 지우지 않는다

429 는 응답의 성질이다. 요청은 이미 나갔고 그 URL 에 필요한 것이 전부 들어 있었다. 실패한 시도가 남긴 잔해를 뒤지는 것 — 이번 문제의 열쇠가 거기 있었다.

3

같은 자원이라도 표현마다 정책이 다르다

같은 호스트, 같은 토큰인데 타일은 429, photo 는 200. 엔드포인트를 하나의 덩어리로 모델링하면 이 틈이 안 보인다. “막혔다”고 할 때는 무엇이 막혔는지 한 단계 더 쪼개 본다.

4

원인을 관측할 수 없으면 결과를 관측한다

워커 요청은 페이지에서 안 보인다. 그러면 요청 말고 화면을 본다. 관측 지점이 막혔을 때 필요한 것은 더 나은 도구가 아니라 다른 각도일 때가 많다.

5

제약을 센서로 뒤집어 쓴다

캔버스 오염은 원래 장애물이다. 그런데 오염됐다는 사실 자체가 “교차출처 이미지가 들어왔다”는 증거다. 막고 있던 것이 그대로 판별자가 됐다. 제약을 만나면 “무엇을 못 하게 하는가” 다음에 “그 존재가 무엇을 알려 주는가”를 묻는다.

6

의미를 바꾸는 조용한 폴백은 눈에 보이는 실패보다 나쁘다

공식 파노 대체는 화면을 채우지만 다른 장소를 분석한다. 검은 화면은 사용자가 알아채지만, 바꿔치기된 장면은 알아채지 못한다. 폴백은 의미를 보존할 때만 폴백이다. 아니면 그건 조용한 오답 생성기다.

7

불가능한 소요 시간은 버그 신고다

브라우저를 띄우는 엔드포인트가 0.15초에 답했다. 값이 그럴듯해도 시간이 물리적으로 말이 안 되면 그 경로는 실행되지 않은 것이다. 반대 방향(1181초)도 같은 신호다. 결과값과 함께 소요 시간을 본다.

8

비동기 결과에는 정체성을 함께 들고 다닌다

10초짜리 조회가 돌아왔을 때 “아직 유효한가”를 플래그로 판단하면 이벤트 순서에 진다. 요청 시점의 ID 와 현재 ID 를 비교하면 이긴다. 정확성과 안전성을 동시에 준다 — 늦게 온 이미지가 엉뚱한 장소를 덮는 일이 구조적으로 불가능해진다.

9

재현 장치도 코드다 — 대조군으로 검증한다

page.route 는 “429 를 받는 상태”가 아니라 “요청이 소멸한 상태”를 만들었다. 기준선(개입 없이 15건 200)을 먼저 재 뒀기 때문에 알아챌 수 있었다. 재현이 목표 상태를 진짜로 만들었는지 매번 확인한다.

10

측정은 대상을 오염시킨다

반복 검증이 API 제한과 메모리 고갈을 불렀고, 그 구간의 결과는 전부 무효였다. 정상 대조군을 다시 돌려 환경 문제와 코드 문제를 가른다. 흔들리는 환경에서 여러 번 돌려 평균 내지 않는다 — 판정은 한 번의 깨끗한 실행으로.

11

사용자가 겪는 층에서 눈으로 확인한다

“타일 200 이 왔다”는 화면이 보인다는 뜻이 아니다. 실제로 앱을 띄워 링크 붙여넣기 → 추출 → 로드뷰까지 태우고 스크린샷을 남겼다. 이 전환은 사용자의 한 문장(“직접 눈으로 확인하면 안 되는가”)에서 왔다. 대리 지표에 오래 머무르면 부품만 고치고 물건은 못 고친다.

12

부정 결과도 기록한다

getTileUrl 은 존재하지 않았다. 그 기록이 다음 사람의 시간을 아끼고, 무엇보다 실패가 다음 가설의 형태를 정해 줬다 — 합성이 막혔으니 관측으로. 막다른 길도 지도의 일부다.

한계현재 상태영향
토큰 조회 콜드 9.4초파노당 1회 · 세션 캐시 제3자 파노를 처음 열 때만. 이후 0.13초.
