Methodology

먼저 원칙 — 사례에서 뽑아낸 것

아래 아홉 개는 이번 세션에서 실제로 결과를 갈랐던 판단들이다. 추상적으로 좋은 말이 아니라, 지키지 않았을 때 내가 틀렸던 지점들이다.

1

"내 변경 탓인가"를 가장 먼저 끊어라

새 코드를 넣은 직후 무언가 깨지면 본능적으로 내 변경을 의심한다. 그 의심은 값이 싸지만 검증은 더 싸다. 변경 이전 커밋을 그대로 실행해 보면 1분 만에 범위가 반으로 준다. git worktree add $TEMP/orig HEAD 는 작업 트리를 건드리지 않고 이걸 해 준다.

2

추론 대신 이분 탐색으로 경계를 좁혀라

create_default_context() 가 죽는다는 사실만으로는 아무것도 못 고친다. 그 함수가 하는 일을 단계별로 따로 호출하면 죽는 지점이 한 줄로 특정된다. "왜 죽을까"를 생각하는 시간보다 "어디서 죽나"를 재는 시간이 짧다.

3

종료 코드는 자가 종료와 타살을 구분해 준다

exit 1 이면 프로세스가 ExitProcess 를 스스로 불렀다는 뜻이고, 0xC0000005 면 액세스 위반, 0xC000013A 면 외부 종료 요청이다. 이 하나로 "누가 죽였나"라는 질문 자체가 사라진다.

4

부재를 증명하려면 계측을 먼저 의심하라 내가 틀린 지점

"타일 요청이 0건"은 요청이 없다는 뜻이 아니라 내 필터가 못 봤다는 뜻일 수 있다. 무언가가 "없다"는 관측은 언제나 계측기의 성능 한계와 구분되지 않는다. 부재를 주장하기 전에 같은 계측기로 존재를 잡아 보여라(대조군). 그게 안 되면 그 계측은 부재의 증거가 못 된다.

5

대조군 없는 측정은 측정이 아니다

제3자 파노가 검다는 관측은 공식 파노가 밝다는 짝이 있어야 의미를 갖는다. 쿠키 동의 화면에 막혔을 때 세 케이스가 전부 밝기 248.3 으로 같았던 것이 그 테스트가 무효임을 즉시 알려 줬다. 대조군은 결론을 위해서가 아니라 측정의 유효성 검사를 위해 있다.

6

코드를 읽어 추론하지 말고 돌려서 재현하라

파일명 충돌은 _report_filename() 을 읽고 "충돌할 수 있겠다"고 말할 수도 있었다. 대신 실제로 스레드 5개를 동시에 돌렸다. 추론은 반박 가능하지만 재현은 그렇지 않고, 재현 스크립트는 그대로 회귀 테스트가 된다.

7

화면에 뜬 문자열을 코드베이스에서 검색하라

"보고서 실패: Not Found" 에서 접두사가 새 코드에 존재하지 않는다는 사실 하나로 "지금 돌고 있는 건 옛 JS"가 즉시 확정됐다. 그래서 사용자에게 보이는 문자열은 코드베이스에서 유일해야 한다 — 그 자체가 버전 식별자다.

8

프로세스의 바깥 상태를 관찰하라

1181초 작업이 무엇을 하는지는 코드를 봐서는 알 수 없다. 열린 TCP 연결의 생성 시각이 작업 시작 시각과 일치한다는 것, CPU 46초/22분 이라는 것 — 이 둘이 "스핀이 아니라 단일 요청 대기"를 증명했다. 재연결이 없으니 SDK 재시도도 아니다.

9

검증자가 나를 반박하면, 반박을 검증하라 — 어느 쪽도 그냥 믿지 말고 내가 틀린 지점

워크플로가 내 결론을 정면으로 반박했을 때, 받아들이지도 무시하지도 않고 직접 재측정했다. 1차 재측정은 내 원래 결과를 재현했고(내가 맞는 듯했다), 그러나 그 계측에도 같은 종류의 결함이 있었다. 필터를 완전히 제거한 3차 측정에서야 진실이 나왔다. 반박을 검증하는 과정에서 내 계측의 결함이 드러난 것이다.

Case 1

서버가 배너 한 줄도 못 찍고 죽는다

적용 원칙: ① 내 변경 끊기 · ② 이분 탐색 · ③ 종료 코드

증상

OPENSSL_Uplink(...): no OPENSSL_Applink

관찰
stdout 비어 있음. stderr 한 줄. 프로세스 즉시 종료. 그런데 같은 날 21:03 에 캡처가 정상 생성된 이력이 있다.
질문
방금 내가 넣은 변경 때문인가?
시도 1
변경 이전 커밋을 격리 실행. 작업 트리를 건드리지 않으려고 worktree 를 썼다. 
git worktree add $TEMP/geo_orig HEAD
# → ORIGINAL(HEAD) stderr:
OPENSSL_Uplink(00007FFCDAFEAC60,08): no OPENSSL_Applink
원본도 죽는다 → 내 변경과 무관. 여기서 탐색 범위가 절반으로 줄었다.
질문
외부가 죽이는가, 스스로 죽는가?
시도 2
종료 코드 확인. exit 1 — ExitProcess(1) 자가 종료다. 액세스 위반(0xC0000005)도 외부 종료(0xC000013A)도 아니다. "누가 죽였나"라는 질문 자체가 여기서 소멸했다.
질문
그 함수의 어느 부분이 죽는가?
시도 3
구성 단계를 하나씩 따로 호출. 추론하지 않고 잘랐다. 
SSLContext(PROTOCOL_TLS_CLIENT)   통과
enum_certificates('ROOT')          통과
set_default_verify_paths()         통과
load_default_certs()               통과
create_default_context()           사망
CA 번들 로드까지 전부 통과 → create_default_context() 가 추가로 하는 일이 범인이다. CPython 소스에서 그건 딱 한 줄이었다. 
# Lib/ssl.py:725
keylogfile = os.environ.get('SSLKEYLOGFILE')
발견
프로세스 환경 : \\.\aswMonFltProxy\3e7f7b040b43e88d  ← Avast 필터 드라이버
사용자 환경   : (없음)
시스템 환경   : (없음)   ← 레지스트리가 아니라 런타임 주입
Avast 가 HTTPS 검사를 위해 세션 키 로그 경로를 주입 → CPython 이 그 경로를 fopen() → OpenSSL BIO_new_fp() → 정적 링크 빌드에 OPENSSL_Applink 부재 → ExitProcess(1).
오판
중간에 PATH 에서 C:\WINDOWS\system32\libcrypto.dll 을 발견하고 "DLL 충돌"이라고 단정했다. 틀렸다. 프로세스 모듈을 EnumProcessModules 로 열거하니 OpenSSL DLL 이 하나도 로드되지 않았다(정적 링크 빌드). 가릴 대상 자체가 없었다. — PATH 에 있다는 것과 로드됐다는 것은 다르다. 후자를 재야 한다.
검증
변수를 지우자 즉시 통과: create_default_context() 통과! exit=0. 단일 변수 제거로 증상이 사라짐 → 인과 확정.
수정. tls.neutralize_keylog() — 프로세스 환경에서만 제거한다. 시스템 설정은 건드리지 않는다. 지우는 것이 안전한 이유는 그 값이 기능 설정이 아니라 "TLS 세션 키를 이 디바이스로 흘려라"는 지시이고, 남겨두면 ANTHROPIC_API_KEY 가 오가는 연결의 세션 키까지 나가기 때문이다. 상세: docs/error/ssl-openssl-applink-exit_260810.html
Case 2

"보고서 실패: Not Found" — 문자열이 범인을 지목하다

적용 원칙: ⑦ 문자열 추적 · 그리고 내가 만든 회귀를 인정하기

증상

캡처 6장 후 보고서 버튼 → 즉시 실패

유혹
"6"이 max_analyze_images = 6 과 같다. 여기서 시작하면 몇 시간을 버린다.
질문
이 문자열은 어느 코드가 만드나?
시도 1
"보고서 실패: " 를 코드베이스에서 검색 → 새 프론트엔드에 없다. 새 코드는 "작업 등록 실패: " 를 쓴다. 옛 app.js 에만 있다.
→ 브라우저가 캐시된 예전 JS 를 실행 중이라는 것이 이 시점에 확정.
그리고 "Not Found" 는 FastAPI 의 기본 404 본문 {"detail":"Not Found"} 의 값이다. 앱이 만든 메시지가 아니다.
시도 2
라우트 목록을 찍었다. 요청 본문이 아니라 라우팅을 의심해야 하는 상황이니까. 
/api/report                없음  ← 404 원인
/api/scene-report          없음  ← 404 원인
/api/jobs/report           있음
내 잘못
큐를 도입하며 구 경로를 없앴는데, 새 server.py docstring 에는 "호환 래퍼로 남긴다"고 써놓고 구현하지 않았다. 문서가 코드보다 앞서 나간 그 격차가 그대로 버그가 됐다. 게다가 정적 파일에 캐시 무효화 장치가 없어 "새 서버 + 옛 프론트" 조합이 만들어질 수 있었다.
수정
① 구 경로를 같은 큐를 지나되 완료까지 기다리는 래퍼로 복원(순차 보장 유지). ② app.js?v=0.2.0 캐시 무효화 도입. 
POST /api/report → HTTP 200  status:FAIL
  message: "분석할 캡처 이미지가 없습니다."   ← 앱이 만든 진짜 메시지
  jobId  : job_f10ee8e4db8d                ← 큐를 지났다는 증거
교훈. 404 는 "서버가 그 경로를 모른다"는 뜻이다. 요청 본문·데이터 문제로 착각하면(이번엔 "캡처 6장") 엉뚱한 곳을 판다. 라우트 목록을 먼저 찍는 것이 가장 빠르다. 그리고 공개 API 경로는 지우지 말고 남겨라 — 클라이언트(브라우저 캐시 포함)를 서버와 동시에 갱신할 수 없기 때문이다.
Case 3

보고서가 사라진다 — 추론 대신 재현

적용 원칙: ⑥ 재현 · 재현 스크립트를 그대로 회귀 테스트로

가설

파일명이 같으면 조용히 덮어써진다

코드
report_{iso}_{장소}_{위도}_{경도}_{yymmdd}_{hhmmss}_{언어}.html
좌표는 소수점 4자리(≈11m), 시각은 초 단위. 그리고 out.write_text() 는 존재 확인이 없다.
질문
"충돌할 수 있다"가 아니라 정말 충돌하는가?
시도 1
같은 초·1.3m 차이 좌표로 파일명 두 개를 실제로 만들었다. 
runA : report_kr_seoul_37.5665_126.978_260809_214429_ko.html
runB : report_kr_seoul_37.5665_126.978_260809_214429_ko.html
SAME FILENAME? True
시도 2
스레드 5개로 동시 쓰기 — 수정 후 회귀 테스트가 될 형태로 짰다. 
수정 후
  동시 5건 → 디스크 파일: 5
    ..._ko.html    run 0
    ..._ko-2.html  run 1
    ..._ko-3.html  ..._ko-4.html  ..._ko-5.html
  모두 보존됨: True   (예전엔 1개만 남았다)
  임시파일 잔여: none
부수 발견
재현하다 두 번째 결함이 드러났다. country_iso 가 비고 국가명이 비ASCII 면 슬러그가 통째로 날아가 location 이 된다 — 파일명이 대상을 전혀 식별하지 못하고, 충돌 조건이 "같은 장소"에서 "같은 초" 로 넓어진다. 
iso 없음 + 대한민국 : c4f12e8
iso 없음 + 日本     : c44da6b
서로 다른가         : True   (예전엔 둘 다 location)
수정
O_CREAT|O_EXCL 로 이름을 원자적으로 선점하고, 임시 파일에 다 쓴 뒤 os.replace 로 교체(교체는 원자적). 이로써 덮어쓰기와 "쓰는 중 GET 하면 잘린 HTML 이 200 으로 나가는" 문제가 함께 해결됐다.
왜 재현이 추론보다 나은가. 추론은 "그럴 수 있다"에서 멈추고 반박 가능하다. 재현은 확정이고, 부수 결함을 덤으로 발견하며(위의 슬러그 문제), 무엇보다 수정을 증명하는 도구가 그대로 남는다. 위 스크립트는 지금도 회귀 테스트다.
Case 4

1181초짜리 보고서 — 바깥에서 관찰하기

적용 원칙: ⑧ 프로세스 외부 상태 · 그리고 내가 만든 구멍

증상

보고서가 20분 넘게 끝나지 않는다

시도 1
먼저 로그를 봤다. 큐가 모든 단계 전환을 jsonl 로 남기게 만들어 둔 덕에 코드를 읽지 않고 병목이 나왔다. 
+   0.0초  analyze     장면 분석 중… (8장 · English)
+  30.7초  analyzed    식별: Takaoka / Oyabe area
+   0.0초  research    웹 리서치 중… (English)
+ 418.7초  researched  리서치 완료 — 검색 3회      ← 병목
+  70.6초  translate   Français 번역 중…
+  54.1초  render      보고서 작성 중…
관찰 가능성은 사후에 만들 수 없다. 미리 심어 둔 것만 쓸 수 있다.
질문
멈춘 작업은 무엇을 기다리는가?
시도 2
프로세스 바깥을 관찰. 코드로는 알 수 없는 것들이다. 
TCP  Established  2607:6bc0::10:443  생성 01:05:09
작업 시작                              01:05:09   ← 정확히 일치
CPU  46초 / 22분                                  ← 스핀 아님, 대기
재연결 없음                                        ← SDK 재시도 아님
단일 스트리밍 요청이 22분째 안 끝나는 중.
시도 3
서버 프로세스 시작 시각 vs 파일 수정 시각을 비교. 
서버 시작 : 00:18:58
llm.py    : 01:02:22   ← 서버가 모르는 코드
config.py : 01:07:38
Python 은 핫리로드하지 않는다 → 지금 도는 서버는 내 최근 변경 이전 코드. 모델 교체가 원인이라는 가설이 여기서 죽었다.
내 잘못
내가 스트리밍으로 전환하며 만든 구멍이었다. httpx.Timeout(600) 은 청크 간격이지 총 소요가 아니다. 서버측 web_search 가 도는 동안 keepalive 가 계속 오므로 그 타임아웃은 영영 걸리지 않는다. 취소도 단계 경계에서만 확인해서 호출 안에 들어가면 못 멈췄다. concurrency=1 이라 뒤의 3건이 통째로 막혔다.
수정
스트림 이벤트를 직접 돌며 벽시계 경과와 취소를 확인한다. 
벽시계 상한: 1.02초 만에 중단  (deadline 1.0s)

© 2026 Google        밝기 117.1   타일 16건
© Dragan CVIJETIC    밝기   1.2   타일  0건

깨끗한 대조. 여기서 나는 "제3자는 타일을 아예 요청하지 않는다" 고 결론지었다.
오판 ①
"0건"을 사실로 받아들였다. 계측기를 의심하지 않았다. 내 리스너는 이렇게 필터링하고 있었다: 
if "streetviewpixels" in u or "cbk" in u or "panoid" in u.lower():
제3자 타일의 실제 URL 은 lh3.googleusercontent.com/gpms-cs-s/... — 세 패턴 중 어느 것도 매칭되지 않는다. 공식 파노가 16건으로 잡힌 것이 "계측기가 정상"이라는 거짓 확신을 줬다. 계측기는 한쪽 종류만 볼 수 있었던 것이다.
오판 ②
그 위에서 사용자에게 "라이선스된 API 로는 불가능하고 ToS 위반 스크래핑만 동작한다" 고 보고했다. 실제로 google.com/maps 헤드리스 렌더가 동작하는 것을 확인했고 (밝기 72.8·125.8, lh3 타일 확인), 그것이 유일한 길이라고 말했다. 사용자에게 불필요한 ToS 판단을 요구한 셈이다.
중간에 잡아낸 무효 측정. google.com/maps 테스트 1차는 세 케이스가 전부 밝기 248.3 으로 동일했다. 결론이 아니라 쿠키 동의 화면을 찍은 것이다. 대조군이 없었다면 "전부 렌더된다"고 잘못 읽었을 것이다 — 대조군은 결론이 아니라 측정의 유효성을 지킨다.
2라운드

반박 — 그리고 반박의 검증

반박
백그라운드 워크플로(에이전트 21개)가 정면으로 반박했다: "제3자 파노는 정상 렌더된다(10/10). '0건'은 계측 결함이다." 같은 파노를 밝기 101.9 / 67.3 으로 측정했다고 보고했다.
질문
누구를 믿는가? — 어느 쪽도 믿지 않는다. 직접 잰다.
재측정 1
내 원래 결과가 그대로 재현됐다. 밝기 1.2 / 1.1, 이미지 응답 0건. 이 시점에 "에이전트가 틀렸다"고 결론지을 수 있었다. 그러나 내 새 계측도 content-type 에 image 가 든 응답만 세고 있었다. 429 오류 응답은 이미지가 아니다. 같은 종류의 결함이 반복된 것이다.
재측정 2
필터를 전부 제거하고 호스트별·상태코드별로 모든 응답을 셌다. 
© Dragan   lh3.googleusercontent.com  HTTP 429 ×1   → 검정
© Henry    lh3.googleusercontent.com  HTTP 429 ×8   → 검정
© Google   streetviewpixels-pa        HTTP 200 ×16  → 정상
요청은 있었다. 두 겹의 필터(호스트 패턴 + content-type)에 모두 걸러졌을 뿐이다.
진실
제3자 파노도 Maps JS API 로 정상 렌더된다. 다만 타일이 키 없는 CDN(lh3) 에서 오고, 그 CDN 은 IP 단위 제한이 있다. 내가 밤새 파노 테스트를 몰아 돌린 탓에 429 가 걸려 검게 나왔던 것이다. 워크플로 에이전트는 제한이 풀린 시점에 측정해 101.9 를 봤다. 두 측정 모두 맞았고, 원인 해석만 내가 틀렸다.
파생 피해
잘못된 진단 위에 만든 수정도 잘못이었다. 나는 "제3자면 무조건 근처 공식 파노로 전환" 을 넣었는데, 이건 요청한 지점이 아닌 곳을 조용히 분석하게 만든다. 지오게서 복기 도구에서 최악의 실패다. 게다가 반환 좌표가 요청값 그대로여서 분석기가 다른 거리를 보면서 요청 좌표라고 믿을 수 있었다.
최종 수정
미리 재단하지 않는다. 요청받은 파노를 그대로 렌더하고, 픽셀로 검은지 판정하며, 429 가 있으면 TILES_RATE_LIMITED 로 구분한다. 그때만 공식 파노로 1회 재시도하고, 대체가 일어나면 실제 렌더된 pano·좌표·저작권을 반환하며 substituted=True 로 명시한다. 
제3자(429) → 대체 True, 렌더 pano Xta4ugN_QRTIo3XDFLujgw, © 2026 Google
공식       → 대체 없음, 요청 pano 그대로, 타일 18/18 HTTP 200
이 사례의 핵심. 나는 계측 결함으로 두 번 틀렸고, 두 번째는 반박을 검증하는 과정에서 같은 실수를 반복했다. "요청이 0건"이라는 관측은 요청이 없다와 내가 못 봤다를 구분하지 못한다. 부재를 주장하려면 필터를 걷어내고 다시 재야 한다. 공식 파노가 정상으로 잡힌다는 사실은 계측기 전체가 정상이라는 증거가 아니었다 — 한 종류만 볼 수 있는 계측기였을 뿐이다.

적대적 검증을 설계하는 법

단순히 "검토해 줘"는 확증 편향을 증폭한다. 이번에 쓴 구성은 이렇다:

  • 차원을 나눈다 — 프론트 경합 / 백엔드 동시성 / 파일 정체성 / E2E 타임라인. 한 에이전트가 전부 보면 각 영역이 얕아진다.
  • 발견마다 별도 검증자를 붙인다 — 그리고 렌즈를 달리한다: 정확성(코드가 정말 그런가) · 기존 가드(이미 막혀 있지 않은가) · 재현성(타이밍상 가능한가).
  • 기본값을 "반증"으로 둔다 — refuted=true 를 기본으로 하고, 직접 재현했을 때만 뒤집게 한다. 그러지 않으면 검증자가 원 주장에 동조한다.
  • 다수결로 살린다 — 3개 렌즈 중 2개가 살려야 통과. 이번엔 45건 중 13건이 걸러졌고, 그중에는 내가 강하게 믿던 것도 있었다.

Takeaways

정리 — 다시 한다면

  • 관찰 가능성은 사후에 만들 수 없다. 1181초 병목을 즉시 특정할 수 있었던 것은 큐가 단계 전환을 미리 남기고 있었기 때문이다. 로그는 버그가 나기 전에 심어야 한다.
  • 수정보다 재현이 먼저다. 재현 스크립트는 수정을 증명하고, 그대로 회귀 테스트가 되며, 부수 결함을 덤으로 찾아 준다.
  • 내 변경을 먼저 배제하는 데 1분을 써라. 그 1분이 탐색 범위를 절반으로 줄인다.
  • 사용자에게 보이는 문자열을 유일하게 유지하라. 그것이 "지금 도는 게 어느 버전인가"에 대한 가장 빠른 답이다.
  • 공개 API 경로는 지우지 말고 위임시켜라. 클라이언트를 서버와 동시에 갱신할 수 없다.
  • docstring 에 쓴 약속은 구현과 같은 커밋에. 문서가 코드보다 앞서 나가면 그 격차가 버그다.
  • "없다"는 관측을 가장 강하게 의심하라. 이번 세션의 두 오진 모두 여기서 나왔다. 부재는 계측 한계와 원리적으로 구분되지 않는다.
  • 대조군이 통과했다고 계측기가 정상인 것은 아니다. 공식 파노 16건이 잡혔다는 사실은 "한 종류는 볼 수 있다"만 증명한다. 다른 종류를 볼 수 있는지는 별도로 증명해야 한다.
  • 불확실한 진단 위에 수정을 쌓지 마라. "제3자면 공식으로 전환"은 진단이 틀리자 요청하지 않은 장소를 조용히 분석하는 더 나쁜 버그가 됐다.
  • 모르면 모른다고 말하라. "불가능하다"고 단정해 사용자에게 불필요한 ToS 판단을 요구했다. "아직 확인하지 못했다"가 정확한 표현이었다.
한 문장으로. 이번 세션에서 나를 가장 많이 구한 것은 영리한 가설이 아니라 가설을 죽이는 값싼 실험이었다 — worktree 실행 1분, 종료 코드 확인 10초, 단계 분해 호출 2분. 반대로 나를 두 번 틀리게 한 것은 계측기를 검사하지 않고 계측 결과를 믿은 것이었다.
